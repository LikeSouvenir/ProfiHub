# 4. Подробная схема работы модуля авторизации

Это отдельный, самый весомый по деталям пункт — критерий прямо требует, чтобы работа модуля была **понятна** и **соответствовала требованиям безопасности**. Ниже — универсальный разбор: какие вообще бывают модели авторизации в блокчейн-проектах, а не одна конкретная схема "как в примере с голосованием". На защите выберите одну модель, релевантную своей теме, и разберите её до деталей — этого требует балл 3.

## Шаг 0. Разведите два разных вопроса
Прежде чем рисовать схему, чётко разделите на слайде:
- **Аутентификация** — кто это (доказательство владения ключом/аккаунтом).
- **Авторизация** — что этому "кто" разрешено (роль, права).

Частая ошибка на защитах — показать только аутентификацию ("вот как подключается кошелёк") и вообще не показать авторизацию (проверку прав) — это даёт максимум балл 1–2, потому что "работа модуля понятна" наполовину.

## Модель А: авторизация подписью сообщения (Sign-In with wallet)
Самая частая модель для публичных сетей (Ethereum и совместимые).

1. Клиент запрашивает у бэкенда/контракта одноразовое случайное значение — **nonce** — привязанное к адресу.
2. Пользователь подписывает сообщение, содержащее nonce, кошельком (MetaMask и т.п.) — приватный ключ никогда не покидает кошелёк.
3. Бэкенд/контракт восстанавливает адрес из подписи (`ecrecover` в Solidity, `ethers.verifyMessage` на бэкенде) и сверяет с ожидаемым.
4. После успешной проверки nonce **инвалидируется** (увеличивается счётчик, помечается использованным) — это критично: без инвалидации подпись можно переиспользовать (**replay-атака**).
5. Дальше выдаётся сессия (например, JWT с коротким сроком жизни) или прямой доступ разрешается на каждый следующий вызов через ту же схему подписи.

**Что обязательно показать для балла 3:** откуда берётся nonce, где именно проверяется подпись (on-chain в контракте через `ecrecover`, или off-chain на бэкенде), что мешает переиспользовать старую подпись, и какой у сессии срок жизни.

## Модель Б: авторизация через приватную/permissioned сеть (API key + keystore ноды)
Актуально для permissioned-платформ (Waves Enterprise/web3tech, Hyperledger Fabric и подобных), где участников сети заранее регистрирует администратор.

1. У каждой ноды есть keystore с парами ключей зарегистрированных участников; на уровне сети выданы permission (кто вообще может слать транзакции).
2. Клиентское приложение обращается к REST API ноды с заголовком авторизации (например, `X-API-Key`) — это доказывает право обращаться именно к этой ноде, а не то, от чьего имени будет отправлена транзакция.
3. Отдельно в теле транзакции указывается `sender` — адрес, от имени которого нода подписывает вызов своим хранящимся ключом.
4. Собственно **авторизация действия** (может ли этот `sender` вызвать именно этот метод) проверяется уже **внутри смарт-контракта** — по ролям, которые контракт сам хранит в своём состоянии (см. Модель Г ниже).

**Что обязательно показать:** два разных уровня доступа — "может ли обращаться к API ноды" и "может ли выполнить это действие в контракте" — это часто путают, и путаница явно видна экспертам в вопросах.

## Модель В: классическая связка логин/пароль + JWT/OAuth2, если есть свой бэкенд
Если в проекте есть собственный бэкенд-сервис между фронтендом и блокчейном (частый случай — нужно скрыть приватный ключ сервисного аккаунта, агрегировать данные с нескольких контрактов и т.д.):
1. Пользователь логинится классическим способом (логин/пароль, OAuth2 через внешнего провайдера) — бэкенд выдаёт **JWT** с полезной нагрузкой (`sub`, `role`, `exp`).
2. Каждый следующий запрос к бэкенду несёт JWT в заголовке `Authorization: Bearer ...`.
3. Бэкенд проверяет подпись и срок действия токена, затем от **своего** сервисного ключа (или ключа, привязанного к этому пользователю) отправляет транзакцию в блокчейн.

Эта модель хуже с точки зрения децентрализации (бэкенд — точка отказа и точка доверия), но абсолютно нормальна для MVP на хакатоне — важно на слайде явно признать этот компромисс, а не выдавать его за полностью децентрализованное решение.

## Модель Г: контроль доступа внутри самого смарт-контракта (Role-Based Access Control)
Работает поверх любой из моделей выше — это то, что происходит **после** того, как система узнала адрес отправителя.
```
mapping(address => Role) roles;

modifier onlyRole(Role required) {
    require(roles[msg.sender] == required, "Access denied");
    _;
}

function registerParticipant(address who, Role role) external onlyRole(Role.ADMIN) {
    roles[who] = role;
}
```
Тот же паттерн в Waves Enterprise (Java) выглядит как явная проверка в начале метода:
```java
User admin = USERS.get(call.getCaller());
if (!Objects.equals(admin.role, Role.ADMIN)) throw new RuntimeException("Access denied");
```
Принцип один и тот же независимо от платформы: **кто вызывает → есть ли такая учётная запись → активна ли она → есть ли нужная роль**. Это и есть содержательный ответ на "как работает авторизация" — не просто "юзер логинится", а конкретный алгоритм проверки прав перед каждым изменяющим действием.

## Чек-лист требований безопасности (то, что явно проверяют эксперты)
- [ ] Защита от replay-атак (nonce, инвалидация подписи/токена после использования)
- [ ] Ограниченный срок жизни сессии/токена, а не бессрочный доступ
- [ ] Приватные ключи никогда не передаются на бэкенд/во фронтенд в открытом виде в проде (объясните, если в вашем прототипе это временное упрощение — так и скажите: "в проде вынесли бы подпись на клиент/в отдельный сервис ключей")
- [ ] Разделены роли минимум "администратор" и "обычный участник" — иначе демонстрировать нечего в вопросе "а как ограничены права"
- [ ] Показано, что происходит при попытке неавторизованного действия (ошибка, revert, а не молчаливый пропуск)

## Пример на разных доменах
- **DAO-голосование:** авторизация через подпись кошелька + вес голоса определяется балансом токена управления на момент снапшота (а не в реальном времени — иначе можно занять токены прямо перед голосованием и продать сразу после).
- **Логистика:** API key + роли участников (поставщик/оператор/клиент), назначаемые администратором сети вручную при подключении новой организации.
- **Реестр сертификатов:** право "выпустить сертификат" есть только у адресов аккредитованных учебных заведений — список таких адресов хранится в контракте и обновляется мультиподписью (несколько доверенных сторон должны согласовать добавление нового заведения).
