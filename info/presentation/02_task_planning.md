# 2. Планирование всех задач проекта

## Что судьи хотят увидеть
По критерию два независимых требования, и балл 3 требует выполнения **обоих**: (а) все подзадачи сформулированы, (б) время между ними распределено, причём распределено **оптимально** — не просто поровну, а с учётом зависимостей и приоритетов.

## Как декомпозировать проект на задачи
Идите сверху вниз от функциональных требований из ТЗ:
1. Возьмите каждое требование "роль может действие" из ТЗ.
2. Разбейте его на слой: смарт-контракт (бизнес-логика) → бэкенд/скрипты взаимодействия → фронтенд (форма/страница) → тесты.
3. Отдельно вынесите сквозные задачи, которые не привязаны к одной функции: настройка окружения/сети нод, деплой, написание общих утилит (например, единый метод отправки транзакций, как `post()` в примере фронтенда), написание презентации.

## Как показать это на слайде
Два рабочих формата — выбирайте тот, что нагляднее ляжет на конкретный проект:

**Диаграмма Ганта** — хороша, когда задачи выполняются параллельно командой и важны зависимости по времени:
```
Задача                     | Час 1 | Час 2 | Час 3 | Час 4
Контракт: роли/пользователи|███████|       |       |
Контракт: бизнес-методы    |       |███████|███    |
Деплой и настройка сети    |███    |       |       |
Фронтенд: авторизация      |       |███    |       |
Фронтенд: формы методов    |       |       |███████|
Тестирование сценария      |       |       |       |███████
```

**Kanban-доска (To do / In progress / Done)** — лучше показывает текущий статус на момент презентации, особенно если часть задач не успели доделать (это нормально — честно показать реальный прогресс лучше, чем скрыть):
```
To do              | In progress          | Done
--------------------|----------------------|--------------------
Мультиязычность UI | Тесты edge-case      | Контракт: init
                    | Обоснование блокчейна| Контракт: роли
                    |                       | Деплой в сеть
```

## Оптимальное распределение времени — что это значит
"Не оптимально" (балл 2) — это когда задачи идут строго последовательно, хотя часть из них не зависит друг от друга (например, фронтенд формы можно верстать параллельно с написанием контракта, а не после его полного завершения). "Оптимально" (балл 3) — когда на диаграмме видно, что независимые задачи идут параллельно, а последовательно идут только те, что реально зависят друг от друга (нельзя писать фронтенд-форму вызова метода, пока не зафиксирована сигнатура метода в контракте).

## Частые ошибки
- Задачи сформулированы, но без оценки времени и порядка — это максимум балл 1 ("выполнен один из двух критериев").
- Список задач составлен постфактум, "как это было", без видимой логики приоритизации.
- Все задачи выглядят одинаково важными — не показано, что является критическим путём (без чего презентовать нечего) и что можно было бы не успеть без потери сути проекта.
