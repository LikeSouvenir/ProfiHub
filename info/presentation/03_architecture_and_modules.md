# 3. Архитектура проекта: модули и их взаимосвязь

## Что судьи хотят увидеть
Балл 3 формулируется как "модули указаны, связи установлены, из описания [ясно, как работает система]" — то есть мало нарисовать красивые прямоугольники со стрелками, схема должна **объяснять**, а не иллюстрировать: посмотрев на неё, эксперт должен понимать, как запрос проходит через систему от пользователя до записи в блокчейн.

## Универсальный набор модулей блокчейн-приложения
Почти любой проект на хакатоне раскладывается на одни и те же слои — используйте их как каркас, а не изобретайте структуру с нуля:

1. **Клиент (фронтенд)** — форма ввода, отображение состояния.
2. **Слой авторизации** — определяет, кто отправляет запрос (подробно — файл 04).
3. **Транспортный/API-слой** — то, через что клиент обращается к блокчейну: REST API ноды, gRPC, JSON-RPC, или бэкенд-прослойка между фронтом и нодой.
4. **Смарт-контракт(ы)** — бизнес-логика и правила.
5. **Хранилище состояния** — то, что живёт непосредственно в блокчейне (state контракта, storage EVM-контракта).
6. **Внешние сервисы (опционально)** — оракулы, индексаторы (The Graph, GoldSky), файловое хранилище (IPFS) для больших данных, которые не кладут прямо в блокчейн.

## Как рисовать схему, чтобы она "объясняла"
- Каждый прямоугольник — это модуль с чётко подписанной **ответственностью** ("Контракт Registry: хранит организации и пользователей", а не просто "Контракт 1").
- Каждая стрелка подписана **типом взаимодействия**: "HTTP POST /transactions/signAndBroadcast", "вызов метода registerOrg()", "чтение через events" — просто линия без подписи не считается "установленной связью" для эксперта.
- Направление стрелок должно показывать направление **данных или вызова**, а не просто "эти два блока связаны". Если связь двусторонняя (запрос + ответ) — рисуйте две стрелки или одну двунаправленную, но явно.
- Разделяйте on-chain и off-chain части визуально (например, разным фоном) — это подчёркивает понимание того, что реально исполняется в блокчейне, а что — обвязка вокруг него.

## Пример структуры на разных доменах
- **DAO-голосование:** Клиент → Кошелёк/подпись → Контракт токена (баланс = вес голоса) → Контракт голосования (создание/учёт предложений) → события `ProposalCreated`, `Voted`, которые индексирует фронтенд.
- **Логистика (кейс экспортного производства):** Клиент (React-формы) → REST API ноды Waves Enterprise → Docker-контейнер смарт-контракта (Java) → Mapping-состояние (`USERS`, `ORGS`, `BIDS`, `PRODUCTS`) → чтение состояния тем же REST API.
- **Реестр сертификатов:** Бэкенд учебного заведения → подпись транзакции о выпуске сертификата → контракт-реестр (хэш документа + метаданные) → публичная страница проверки, которая читает состояние по хэшу без авторизации.

## Частые ошибки
- На схеме только смарт-контракт, а всё остальное ("а как туда фронт достучался?") остаётся за кадром — это балл 1–2, "работа системы не до конца понятна".
- Модули показаны, но нет ни одной подписи на стрелках.
- Архитектура на слайде не совпадает с тем, что реально показывается в демо графического интерфейса (слайд 7) — эксперты быстро замечают такие нестыковки в вопросах.
