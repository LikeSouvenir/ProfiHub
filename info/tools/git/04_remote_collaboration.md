# Удалённые репозитории и совместная работа

## git clone — скачать существующий репозиторий
```bash
git clone https://github.com/username/repository.git
git clone https://github.com/username/repository.git новая_папка  # с другим именем папки
```
`clone` создаёт полную локальную копию репозитория вместе со всей историей коммитов и автоматически настраивает связь с оригиналом под именем `origin`.

## git remote — работа со связанными репозиториями
```bash
git remote -v                                   # показать все подключённые удалённые репозитории
git remote add origin https://github.com/username/repo.git  # подключить удалённый репозиторий вручную
git remote remove origin                        # отключить удалённый репозиторий
```
`origin` — стандартное, общепринятое имя для "основного" удалённого репозитория, но технически это просто имя-псевдоним, можно назвать иначе.

## git push — отправка коммитов на сервер
```bash
git push origin main             # отправить локальные коммиты ветки main на сервер origin
git push -u origin main          # то же самое + запомнить эту связку (upstream) на будущее
git push                         # после -u достаточно просто "push" — Git запомнил, куда именно
```
- `-u` (`--set-upstream`) связывает локальную ветку с конкретной веткой на удалённом сервере, чтобы в дальнейшем не указывать `origin main` каждый раз.

```bash
git push --force            # принудительная перезапись истории на сервере (ОПАСНО, переписывает чужую работу)
git push --force-with-lease # более безопасный вариант: отменит push, если на сервере появились чужие коммиты, о которых вы не знали
```
*`--force` стоит использовать крайне осторожно — если кто-то ещё уже успел запушить свои коммиты, они будут безвозвратно потеряны на сервере.*

## git pull — получение и слияние изменений
```bash
git pull origin main
```
`pull` фактически выполняет две команды подряд: `git fetch` (скачать новые коммиты с сервера) + `git merge` (влить их в текущую локальную ветку).

```bash
git pull --rebase origin main
```
Вместо обычного слияния переносит (`rebase`) локальные ещё не отправленные коммиты поверх свежескачанных — сохраняет более линейную, "чистую" историю.

## git fetch — только скачать, не сливая
```bash
git fetch origin
```
Скачивает все новые коммиты и ветки с сервера, но **не трогает** текущую рабочую директорию и не сливает их автоматически — позволяет сначала посмотреть, что изменилось (`git log origin/main`), и только потом решить, сливать ли эти изменения.

## Типичный рабочий процесс (workflow) с удалённым репозиторием
```bash
git clone https://github.com/username/repo.git
cd repo

git checkout -b feature-login       # создаём ветку под новую задачу

# ... вносим изменения в код ...

git add .
git commit -m "Добавлена форма логина"

git push -u origin feature-login    # отправляем ветку на сервер

# Дальше на GitHub создаётся Pull Request для code review и последующего слияния в main
```

## Pull Request (PR) — кратко
После `git push` новой ветки на GitHub/GitLab обычно создаётся **Pull Request (Merge Request)** — формальный запрос на слияние ветки в основную. Это не команда Git как таковая, а функция веб-сервиса (GitHub/GitLab), которая:
- показывает все изменения (diff) наглядно в браузере;
- позволяет коллегам оставлять комментарии к конкретным строкам кода (code review);
- запускает автоматические проверки (тесты, линтеры) перед слиянием;
- фиксирует итоговое слияние отдельным, именованным событием в истории проекта.

## Полезные дополнительные команды
```bash
git stash                # временно "отложить" незакоммиченные изменения, не создавая коммит
git stash pop             # вернуть отложенные изменения обратно
git stash list             # посмотреть список всех отложенных "заначек"

git reset --soft HEAD~1    # отменить последний коммит, но оставить изменения в staging area
git reset --mixed HEAD~1   # отменить последний коммит и убрать из staging area (изменения останутся в файлах)
git reset --hard HEAD~1    # отменить последний коммит и ПОЛНОСТЬЮ удалить эти изменения (осторожно!)

git revert коммит_хэш      # создать новый коммит, отменяющий изменения указанного коммита
                            # (безопаснее reset для уже опубликованной истории — ничего не удаляет, а добавляет)

git tag v1.0.0             # пометить текущий коммит как версию (например, релиз v1.0.0)
git cherry-pick коммит_хэш # перенести один конкретный коммит из другой ветки в текущую
```

## Сводная таблица: reset vs revert
| | `reset` | `revert` |
|---|---|---|
| Меняет историю | ✅ Да (переписывает) | ❌ Нет (добавляет новый коммит) |
| Безопасно для общей/опубликованной истории | ❌ Нет | ✅ Да |
| Когда использовать | Локальные, ещё не отправленные коммиты | Коммиты, уже отправленные на сервер и видимые другим |
