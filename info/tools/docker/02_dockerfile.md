# Написание Dockerfile

**Dockerfile** — текстовый файл без расширения (называется именно `Dockerfile`), содержащий пошаговые инструкции: из чего и как собрать Docker-образ.

## Базовый пример: Node.js-приложение
```dockerfile
# Базовый образ — берём готовый образ с установленным Node.js
FROM node:20-alpine

# Рабочая директория внутри контейнера — все следующие команды выполняются относительно неё
WORKDIR /app

# Копируем сначала только файлы зависимостей (для кэширования слоёв, см. ниже)
COPY package*.json ./

# Устанавливаем зависимости внутри контейнера
RUN npm install

# Копируем оставшийся код проекта
COPY . .

# Документируем, какой порт слушает приложение внутри контейнера
EXPOSE 3000

# Команда, которая выполнится при запуске контейнера
CMD ["node", "server.js"]
```

## Разбор основных инструкций

### FROM — базовый образ
```dockerfile
FROM node:20-alpine
```
Каждый Dockerfile начинается с `FROM` — образа, на основе которого строится новый. `alpine` — минималистичный дистрибутив Linux, который часто выбирают за счёт маленького размера итогового образа.

### WORKDIR — рабочая директория
```dockerfile
WORKDIR /app
```
Устанавливает "текущую папку" внутри контейнера для всех последующих команд (`COPY`, `RUN`, `CMD`) — аналог `cd /app`, но фиксируется на уровне всего образа.

### COPY — копирование файлов
```dockerfile
COPY локальный_путь путь_в_контейнере
COPY package*.json ./
COPY . .
```
Копирует файлы с компьютера разработчика (точнее — из "контекста сборки") внутрь образа.

### RUN — выполнение команды при сборке образа
```dockerfile
RUN npm install
RUN apt-get update && apt-get install -y curl
```
Выполняется **один раз, во время сборки образа** — результат (например, установленные зависимости) сохраняется прямо в образе.

### CMD — команда по умолчанию при запуске контейнера
```dockerfile
CMD ["node", "server.js"]
```
Выполняется **при каждом запуске контейнера** (в отличие от `RUN`, который выполняется при сборке). В одном Dockerfile может быть только одна активная инструкция `CMD` — если их несколько, действует только последняя.

### ENTRYPOINT vs CMD
```dockerfile
ENTRYPOINT ["node"]
CMD ["server.js"]
```
`ENTRYPOINT` задаёт "неизменяемую" часть команды запуска, а `CMD` — аргументы по умолчанию, которые можно переопределить при запуске контейнера (`docker run образ другой_файл.js` заменит только `CMD`, оставив `node` из `ENTRYPOINT`).

### ENV — переменные окружения
```dockerfile
ENV NODE_ENV=production
ENV PORT=3000
```
Задаёт переменные окружения, доступные внутри контейнера во время его работы (аналог `process.env.PORT` в Node.js).

### ARG — аргументы сборки
```dockerfile
ARG APP_VERSION=1.0.0
RUN echo "Сборка версии $APP_VERSION"
```
В отличие от `ENV`, `ARG` доступен **только во время сборки образа** и не сохраняется в готовом контейнере. Передаётся при сборке:
```bash
docker build --build-arg APP_VERSION=2.0.0 .
```

### EXPOSE — документирование порта
```dockerfile
EXPOSE 3000
```
Не открывает порт "физически" наружу сам по себе (это делается флагом `-p` при `docker run`), а лишь документирует, какой порт слушает приложение внутри контейнера.

### VOLUME — точка монтирования тома
```dockerfile
VOLUME /app/data
```
Помечает папку внутри контейнера как место для постоянного хранения данных, которые должны переживать удаление и пересоздание контейнера (подробнее про тома — в файле про CLI-команды).

## Кэширование слоёв (layer caching)
Каждая инструкция Dockerfile создаёт отдельный **слой (layer)**. Docker кэширует уже собранные слои и пересобирает заново только те, что изменились (и всё, что идёт после них).

```dockerfile
# ✅ Правильный порядок: зависимости копируются и ставятся ОТДЕЛЬНО от остального кода
COPY package*.json ./
RUN npm install
COPY . .
```
Если поменять только исходный код приложения (не трогая `package.json`), слой с `npm install` останется закэшированным и пересобираться не будет — сборка образа станет значительно быстрее.

```dockerfile
# ❌ Неоптимально: любое изменение кода заставит заново переустанавливать все зависимости
COPY . .
RUN npm install
```

## .dockerignore
Аналог `.gitignore`, но для Docker — исключает ненужные файлы из "контекста сборки", ускоряя `docker build` и уменьшая размер образа:
```
node_modules
.git
.env
*.log
Dockerfile
```

## Многоступенчатая сборка (multi-stage build)
Позволяет использовать несколько `FROM` в одном Dockerfile — например, собрать проект в одном "тяжёлом" окружении, а в финальный образ скопировать только готовый результат, без лишних инструментов сборки:
```dockerfile
# Этап 1: сборка приложения
FROM node:20 AS build
WORKDIR /app
COPY . .
RUN npm install && npm run build

# Этап 2: финальный, лёгкий образ только с готовой сборкой
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
```
Такой подход значительно уменьшает размер итогового образа — все инструменты сборки (компиляторы, dev-зависимости) остаются в промежуточном этапе и не попадают в финальный образ.
