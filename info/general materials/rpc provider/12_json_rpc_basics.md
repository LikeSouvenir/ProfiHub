# RPC-провайдеры: что такое RPC и зачем он нужен

## Проблема, которую решает RPC
Смарт-контракт и данные блокчейна физически лежат в базе данных ноды — но фронтенд, бэкенд-скрипт или мобильное приложение не могут просто "подключиться к базе" напрямую. Им нужен стандартизированный сетевой протокол, через который можно спросить у ноды "какой баланс у этого адреса", "прочитай данные из контракта", "отправь эту подписанную транзакцию в сеть". Этот протокол — **RPC (Remote Procedure Call)**, удалённый вызов процедуры: клиент вызывает метод так, будто он выполняется локально, а на деле запрос уходит по сети на ноду, которая его исполняет и возвращает результат.

Это ровно та же идея, с которой вы уже работали в разделе про Waves — `GET /node/status`, `POST /transactions/signAndBroadcast` — это тоже RPC, просто оформленный как REST API поверх HTTP. В экосистеме Ethereum и большинства EVM-совместимых сетей используется другой, более старый и стандартизированный формат — **JSON-RPC**.

## JSON-RPC 2.0 — формат запроса и ответа
Единый для всех методов конверт: один и тот же HTTP-эндпоинт принимает POST-запросы, а конкретный вызываемый метод указывается внутри тела JSON, а не в пути URL (в отличие от REST, где `/node/status` и `/contracts/{id}` — разные пути).

Запрос:
```bash
curl -X POST https://ethereum-rpc.publicnode.com \
  -H "Content-Type: application/json" \
  -d '{
    "jsonrpc": "2.0",
    "method": "eth_getBalance",
    "params": ["0x0000000000000000000000000000000000dEaD", "latest"],
    "id": 1
  }'
```
Ответ:
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": "0x0"
}
```
`id` — произвольное число, которое клиент сам присваивает запросу и получает обратно в ответе; это нужно, чтобы сопоставлять ответы с запросами, когда несколько вызовов отправляются одновременно (**batching**) или асинхронно по одному соединению.

## Частые методы Ethereum JSON-RPC — ориентир, что вообще можно спросить у ноды
| Метод | Что делает |
|---|---|
| `eth_blockNumber` | номер последнего блока |
| `eth_getBalance` | баланс адреса в нативной валюте сети |
| `eth_call` | выполнить чтение из контракта без записи в блокчейн (бесплатно, без транзакции) |
| `eth_sendRawTransaction` | отправить уже подписанную транзакцию в сеть |
| `eth_getTransactionReceipt` | статус и результат исполнения транзакции по её хэшу |
| `eth_getLogs` | получить события (events), испущенные контрактами, по фильтру |
| `eth_estimateGas` | оценить, сколько газа потребует транзакция, не отправляя её |
| `eth_subscribe` | (через WebSocket) подписаться на поток новых блоков/событий в реальном времени |

Обратите внимание на параллель с тем, что вы уже видели у Waves: `eth_call` ≈ `GET /contracts/{id}` (чтение состояния без транзакции), `eth_sendRawTransaction` ≈ `/transactions/broadcast`, `eth_getTransactionReceipt` ≈ `/contracts/status/{txId}`. Разные платформы, одна и та же логическая структура: прочитать состояние / отправить транзакцию / проверить статус.

## HTTP vs WebSocket
- **HTTP JSON-RPC** — классическая модель запрос-ответ, подходит для разовых вызовов ("какой сейчас баланс").
- **WebSocket JSON-RPC** — постоянное соединение, позволяет **подписаться** на события (`eth_subscribe`) и получать push-уведомления о новых блоках или логах контракта без постоянного опроса (polling). Заметно эффективнее для интерфейсов, которым нужно реагировать на события в реальном времени (например, обновлять список ставок в DAO-голосовании сразу при появлении нового `Voted`-события, а не раз в N секунд опрашивать ноду).

## Full node, light client, archive node — от чего зависит, что вам ответит RPC
- **Full node** — хранит весь текущий стейт и достаточно недавней истории для валидации новых блоков; может ответить на большинство обычных запросов.
- **Archive node** — хранит **всю историю состояния** на каждую высоту блока, а не только текущую — нужна для запросов вида "какой был баланс этого адреса 500 000 блоков назад". Архивные ноды существенно тяжелее в хранении, поэтому у RPC-провайдеров доступ к ним обычно отдельная, более дорогая опция.
- **Light client** — не хранит состояние сам, а запрашивает у полных нод только то, что нужно прямо сейчас, с криптографическим доказательством корректности ответа.

Именно поэтому запуск и поддержка собственной полной (тем более архивной) ноды — не бесплатное и не тривиальное занятие: нужны десятки/сотни гигабайт (для архивной ноды Ethereum — уже терабайты) дискового пространства, постоянная синхронизация с сетью и обслуживание. Отсюда и появляется следующий блок этой темы — **RPC-провайдеры**, которые берут эту инфраструктурную задачу на себя.
