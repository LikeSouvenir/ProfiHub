# Безопасное подключение к RPC и практика

## Главное правило: API-ключ RPC-провайдера — это секрет
API-ключ провайдера определяет, кто платит за запросы и по какому тарифному лимиту — если он утечёт (например, оказался зашит прямо во фронтенд-коде), кто угодно может использовать ваш лимит, исчерпать бесплатный тариф или создать вам неожиданный счёт на платном. Это тот же класс проблемы, что уже разбирался в модуле про презентацию (файл про авторизацию) — секрет не должен путешествовать туда, где его может увидеть посторонний.

### Правильные и неправильные места хранения ключа
- **Неправильно:** `const provider = new ethers.JsonRpcProvider("https://eth-mainnet.g.alchemy.com/v2/МОЙ_КЛЮЧ")` прямо в коде React-компонента — ключ виден в собранном бандле, через DevTools любой посетитель сайта его достанет.
- **Правильно (вариант 1 — свой бэкенд-прокси):** фронтенд обращается к собственному бэкенду (`/api/rpc`), а уже бэкенд, зная ключ из переменных окружения сервера, пересылает запрос RPC-провайдеру и возвращает результат. Ключ никогда не покидает сервер.
- **Правильно (вариант 2 — read-only публичный доступ):** если проект действительно рассчитан на прямой доступ из браузера без своего бэкенда, используйте у провайдера ключ с урезанными правами (только чтение, ограничение по доменам-источникам через allowlist) или общий бесплатный публичный эндпоинт без персонального ключа — это осознанный компромисс для MVP, но не для продакшена с финансовыми операциями.

## Пример настройки провайдера в коде (ethers.js)
```javascript
import { ethers } from "ethers";

// через бэкенд-прокси — ключ остаётся на сервере, фронтенд его не знает
const provider = new ethers.JsonRpcProvider("https://мой-бэкенд.example.com/api/rpc");

// прямое чтение баланса — работает одинаково, независимо от того,
// свой это провайдер-прокси или напрямую RPC-провайдер
const balance = await provider.getBalance("0x0000000000000000000000000000000000dEaD");
console.log(ethers.formatEther(balance));
```
Аналогичная настройка через `viem`:
```javascript
import { createPublicClient, http } from "viem";
import { mainnet } from "viem/chains";

const client = createPublicClient({
  chain: mainnet,
  transport: http("https://мой-бэкенд.example.com/api/rpc"),
});
```

## Паттерн отказоустойчивости: несколько провайдеров с fallback
Раз RPC-провайдер — потенциальная единая точка отказа (см. предыдущий файл), стандартная практика — не полагаться на один эндпоинт:
```javascript
import { ethers } from "ethers";

const providers = [
  new ethers.JsonRpcProvider(process.env.RPC_PRIMARY),
  new ethers.JsonRpcProvider(process.env.RPC_FALLBACK_1),
  new ethers.JsonRpcProvider(process.env.RPC_FALLBACK_2),
];

async function callWithFallback(method, args) {
  for (const provider of providers) {
    try {
      return await provider[method](...args);
    } catch (err) {
      console.warn(`Провайдер недоступен, пробуем следующий: ${err.message}`);
    }
  }
  throw new Error("Все RPC-провайдеры недоступны");
}
```
`ethers.js` также предоставляет встроенный `FallbackProvider`, который делает то же самое автоматически, включая сверку ответов нескольких провайдеров между собой для дополнительной защиты от недобросовестного/скомпрометированного провайдера — полезно упомянуть на защите как более зрелое решение той же задачи.

## Rate limits и как с ними работать
Практически все провайдеры ограничивают число запросов в единицу времени (RPS) и/или суммарный объём в месяц. Типичные признаки упора в лимит — HTTP-код `429 Too Many Requests` или код ошибки `-32005` в теле JSON-RPC ответа. Практические приёмы:
- **Батчинг запросов** — JSON-RPC поддерживает отправку массива запросов одним HTTP-вызовом вместо N отдельных.
- **Кэширование** на бэкенде для данных, которые не меняются каждую секунду (например, метаданные контракта).
- **Экспоненциальный backoff** — при ошибке лимита повторять запрос не сразу, а с увеличивающейся паузой, вместо того чтобы долбить провайдера чаще при уже случившейся перегрузке.

## Чек-лист перед защитой/деплоем
- [ ] API-ключ RPC-провайдера не встречается в клиентском (фронтенд) коде и не закоммичен в git
- [ ] Ключ читается из переменных окружения (`.env`, добавленного в `.gitignore`), а не захардкожен
- [ ] Продумано, что происходит при недоступности провайдера — хотя бы понятная ошибка пользователю, в идеале — fallback на второй провайдер
- [ ] Учтены лимиты бесплатного тарифа при планировании демонстрации на защите (не хочется словить `429` прямо во время доклада)
