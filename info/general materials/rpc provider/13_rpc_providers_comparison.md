# Выбор RPC-провайдера: свой узел или готовый сервис

## Почему почти никто не поднимает свою ноду для разработки
Запуск и синхронизация собственной полной ноды Ethereum занимает от нескольких часов до нескольких дней, требует стабильного canала и десятков-сотен гигабайт места (для архивного режима — терабайты), а дальше требует постоянного администрирования: обновления клиента, мониторинг отставания от сети, резервный канал на случай падения. Для подавляющего большинства прикладных задач (в том числе для хакатона) это неоправданные трудозатраты — вместо этого используют **RPC-провайдера**: сервис, который уже держит парк синхронизированных нод по многим сетям и продаёт доступ к ним через API-ключ.

## Self-hosted нода vs RPC-провайдер — когда что выбирать
| | Своя нода | RPC-провайдер (SaaS) |
|---|---|---|
| Время на старт | Часы-дни на синхронизацию | Минуты — регистрация и API-ключ |
| Затраты | Своё железо/сервер, обслуживание | Подписка/оплата по использованию, часто есть бесплатный тариф |
| Контроль и приватность | Полный — запросы никуда не уходят наружу | Провайдер технически видит все ваши запросы (адреса, вызовы) |
| Надёжность | Зависит от вас — вы сами точка отказа | Обычно SLA, резервирование, глобальное распределение серверов |
| Лимиты | Нет искусственных лимитов запросов | Есть — по количеству запросов/"единиц вычисления" в месяц |
| Архивные данные | Нужно поднимать отдельно, тяжело | Обычно доступны как отдельная опция |

**Практический вывод для хакатона и MVP:** используйте RPC-провайдера — это стандартная практика даже для крупных продакшен-проектов, а не "временное упрощение". Свою ноду поднимают либо по соображениям приватности/суверенности данных, либо при очень большой нагрузке, где выгоднее содержать инфраструктуру самим, чем платить по тарифу.

## Основные игроки на рынке (актуально на 2026 год)
Рынок EVM-совместимых RPC-провайдеров развит и конкурентен — вот ключевые имена, которые стоит знать, и в чём их относительные сильные стороны:

| Провайдер | Сильная сторона | На что обратить внимание |
|---|---|---|
| **Alchemy** | Широкий набор дополнительных API поверх RPC (уведомления, индексация NFT, смарт-кошельки), богатый тулинг для разработчика | Тарификация через "compute units" — вес разных методов разный, нужно считать заранее |
| **Infura** | Старейший и самый "дефолтный" провайдер, глубокая интеграция с MetaMask | Как правило выше задержка ответа, чем у более новых конкурентов |
| **QuickNode** | Ставка на производительность и низкую задержку, глобально распределённая инфраструктура | Хорошо подходит, если критична скорость ответа (например, MEV-чувствительные сценарии) |
| **Chainstack** | Прозрачная тарификация "запрос = запрос" (не взвешенные единицы), сильная сертификация надёжности | Меньше "модного" тулинга поверх голого RPC, чем у Alchemy |
| **Ankr** | Широкая поддержка множества сетей одним аккаунтом | Обычно дороже в пересчёте на реальный вызов по сравнению с конкурентами |
| **Публичные бесплатные эндпоинты** (например, `publicnode.com`, `llamarpc.com`) | Не требуют регистрации вообще | Нет SLA, могут резко ограничивать/блокировать при всплеске трафика — не для продакшена, только для быстрых тестов |

Не привязывайтесь к конкретным цифрам лимитов и цен из статей — рынок быстро меняется, перед началом проекта стоит свериться с актуальной документацией конкретного провайдера.

## А что у платформ вне классического Ethereum-стека
- **Публичный Waves** — REST API нод, как у Waves Enterprise (см. `info/waves/`); есть публичные ноды сообщества (например, `nodes.wavesnodes.com`) — по сути тот же паттерн "не поднимай свою ноду, обратись к чужой", просто без формального понятия "RPC-провайдер" как отдельного бизнеса.
- **Solana** — свой набор RPC-методов (`getBalance`, `getAccountInfo`, `sendTransaction`), тоже JSON-RPC-подобный протокол; собственные RPC-провайдеры под Solana (Helius, QuickNode, публичный `api.mainnet-beta.solana.com` с жёсткими лимитами для прод-нагрузки).
- **Waves Enterprise (permissioned)** — здесь нет внешнего "рынка RPC-провайдеров", потому что сеть закрытая: вы либо сами держите ноду (как участник сети), либо используете ноду, к которой вам выдал доступ администратор сети — концептуально это тот же RPC-слой, просто без коммерческого рынка вокруг него.

## Как выбрать провайдера под учебный/хакатонный проект
1. Для быстрой демонстрации на защите — подойдёт бесплатный тариф любого крупного провайдера (Alchemy/Infura/QuickNode) или публичный бесплатный эндпоинт, если нагрузка минимальна.
2. Если демо предполагает живые события в реальном времени (например, обновление UI сразу при новом голосе) — важна поддержка WebSocket-подписок, это есть у всех крупных платных провайдеров, но не у всех бесплатных публичных эндпоинтов.
3. Если в докладе (модуль Г, файл про уязвимости) вы упоминаете единую точку отказа — RPC-провайдер как раз такая точка: если он ляжет, приложение не сможет обращаться к блокчейну, даже если сама сеть работает нормально.
