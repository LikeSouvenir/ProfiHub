# Что такое индексатор блокчейн-данных

## Проблема, которую решают индексаторы
Нода блокчейна (Geth, любой RPC-провайдер) умеет отвечать только на простые, "точечные" вопросы: баланс конкретного адреса, содержимое конкретного блока, результат вызова конкретной read-функции контракта. Она принципиально **не умеет** отвечать на вопросы вида:
- "Покажи все переводы токена X за последний месяц, отсортированные по сумме"
- "Сколько всего уникальных держателей у этого NFT-коллекшена"
- "Все сделки конкретного пользователя на этой DEX за всё время"

Чтобы ответить на такой вопрос через голый RPC, пришлось бы вручную перебрать **все** блоки за нужный период, вытащить из каждого нужные события (`Transfer`, `Swap`, `Approval`...), самому собрать и агрегировать данные — на практике это очень медленно и требует своей инфраструктуры.

**Индексатор (indexer)** — сервис, который делает эту работу заранее: непрерывно "слушает" блокчейн, вытаскивает нужные события, сохраняет их в удобной для запросов базе данных (обычно с GraphQL или SQL API), чтобы фронтенд или аналитика могли получить ответ на сложный вопрос одним быстрым запросом.

## Общая архитектура любого индексатора
```
Блокчейн (ноды/RPC)
        │  сырые блоки и логи событий
        ▼
 Индексатор (слушает события, парсит их по заданной схеме)
        │  трансформация + агрегация
        ▼
   База данных (Postgres/своя БД)
        │
        ▼
API для запросов (GraphQL или SQL) ──► Фронтенд / аналитика / дашборды
```

## Общие для всех индексаторов понятия
| Термин | Значение |
|---|---|
| **Handler / Mapping** | Код (обычно на TS/AssemblyScript), который вызывается при каждом появлении нужного события и решает, что с ним делать |
| **Schema** | Описание структуры данных, которые индексатор будет хранить (сущности, поля, связи) |
| **Backfill / Historical sync** | Первичная индексация всей истории с указанного стартового блока — может занимать от минут до часов в зависимости от объёма |
| **Reindex** | Полная переиндексация с нуля (например, после изменения схемы или логики обработчиков) |
| **Hosted vs Self-hosted** | Управляемый сервис провайдера vs собственный сервер, поднятый самостоятельно |

## Зачем нужно сразу несколько разных инструментов
Индустрия индексаторов развивалась в разных направлениях: одни делают ставку на децентрализацию и стандартизацию (The Graph), другие — на скорость и простоту self-host (Envio), третьи — на удобство для разработчика через один язык (Ponder, полностью на TS), четвёртые — на тяжёлую SQL-аналитику (Subsquid). Выбор конкретного инструмента — это компромисс между: скоростью синхронизации, удобством написания логики, поддерживаемыми сетями, готовой инфраструктурой хостинга и стоимостью.

## Обзорная сравнительная таблица (подробности — в отдельных конспектах)
| Индексатор | Язык обработчиков | Хостинг | Особенность |
|---|---|---|---|
| **The Graph** | AssemblyScript | Decentralized Network / hosted | Родоначальник подхода, стандарт индустрии (субграфы + GraphQL) |
| **Goldsky** | AssemblyScript (те же субграфы) | Managed | Быстрый managed-хостинг субграфов + стриминг сырых данных в Postgres (Mirror) |
| **Envio (HyperIndex)** | TypeScript | Self-host (Docker) / hosted | Самый быстрый по независимым бенчмаркам синхронизации |
| **Ponder** | TypeScript | Self-host (свой сервер) | Максимально приближен к обычной TS-разработке, любимец инди-разработчиков |
| **Subsquid (SQD)** | TypeScript | Self-host / hosted | Тяжёлый ETL-пайплайн, сильная SQL-агрегация перед выдачей через GraphQL |
| **SubQuery** | TypeScript/AssemblyScript | Self-host / managed | Поддерживает больше всего сетей, включая не-EVM (Polkadot, Cosmos) |
| **Sentio / Ormi / Chainbase** | TypeScript/SQL | Managed (SaaS) | Индексатор + встроенная SQL-аналитика, ориентация на real-time дашборды |

## Как выбирать индексатор на практике
1. **Сеть не EVM-совместима (Cosmos, Polkadot и т.п.)** → SubQuery почти всегда в списке первых кандидатов.
2. **Нужна максимальная скорость первичной синхронизации большого объёма истории** → Envio.
3. **Команда хочет писать всё на TypeScript без изучения нового языка (AssemblyScript)** → Ponder или Envio.
4. **Нужна децентрализация/соответствие индустриальному стандарту, много готовых субграфов для reuse** → The Graph.
5. **Нужен managed-хостинг существующих субграфов The Graph без своей инфраструктуры** → Goldsky.
6. **Нужна серьёзная SQL-аналитика и агрегация "тяжёлых" данных** → Subsquid.
7. **Нужен готовый SaaS с real-time дашбордами без написания собственного индексатора с нуля** → Sentio/Ormi/Chainbase.
