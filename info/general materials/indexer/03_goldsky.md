# Goldsky

## Что это
**Goldsky** — managed-платформа (SaaS), решающая две отдельные задачи: (1) быстрый и надёжный хостинг тех же самых **субграфов The Graph**, без необходимости поднимать и поддерживать собственный Graph Node, и (2) продукт **Mirror** — стриминг "сырых" ончейн-данных напрямую в собственную базу данных (обычно Postgres), в обход GraphQL-слоя вообще.

## Часть 1: Goldsky как managed-хостинг субграфов

### Зачем это нужно, если уже есть The Graph
Развёртывание субграфа в децентрализованной сети The Graph требует токенов GRT, управления индексаторами-кураторами и может быть медленнее на этапе итеративной разработки. Goldsky берёт **тот же самый код субграфа** (тот же `subgraph.yaml`, `schema.graphql`, `mapping.ts`) и хостит его на своей быстрой инфраструктуре — с более простым деплоем и часто более быстрой синхронизацией истории.

### Установка CLI
```bash
npm install -g @goldskycom/cli
goldsky login
```

### Деплой уже существующего субграфа (совместимость с The Graph)
```bash
goldsky subgraph deploy my-erc20-subgraph/1.0.0 --path .
```
Никаких изменений в самом коде субграфа не требуется — Goldsky совместим с форматом The Graph "из коробки", это буквально одна из его ключевых особенностей: миграция с The Graph на Goldsky (и обратно) не требует переписывания обработчиков.

### Проверка статуса синхронизации
```bash
goldsky subgraph list
goldsky subgraph log my-erc20-subgraph/1.0.0
```

## Часть 2: Goldsky Mirror — стриминг сырых данных в Postgres

### Зачем нужен отдельный продукт, если уже есть субграфы
Субграфы хорошо подходят, когда данные нужно **агрегировать и трансформировать** заранее (посчитать балансы, связать сущности). Но иногда нужен противоположный сценарий: получить **все сырые события/транзакции** максимально быстро, напрямую в свою базу данных, чтобы дальше строить аналитику собственными SQL-запросами, без промежуточного GraphQL-слоя и без написания AssemblyScript-обработчиков вообще.

### Конфигурация пайплайна Mirror
```yaml
# pipeline.yaml
name: erc20-transfers-pipeline
sources:
  - type: dataset
    name: ethereum_logs
    dataset_name: ethereum.raw_logs
    filter: "address = '0xАдресКонтракта'"

sinks:
  - type: postgres
    name: my_postgres
    connection:
      host: my-db-host.example.com
      database: indexer_db
      table: erc20_transfers
    from: ethereum_logs
```

### Запуск пайплайна
```bash
goldsky pipeline create erc20-transfers-pipeline --definition pipeline.yaml
goldsky pipeline start erc20-transfers-pipeline
```
После запуска в таблице `erc20_transfers` вашей собственной Postgres-базы начинают появляться строки практически в реальном времени — без единой строчки кода обработчика, только конфигурация источника и назначения (sink).

### Когда выбирать Mirror вместо классического субграфа
| Сценарий | Что выбрать |
|---|---|
| Нужны агрегированные, готовые к использованию сущности (балансы, связи между объектами) | Классический субграф (The Graph или Goldsky-хостинг субграфа) |
| Нужны "сырые" данные максимально быстро в собственной SQL-базе для гибкой аналитики | Goldsky Mirror |
| Команда уже умеет писать SQL, но не хочет разбираться в AssemblyScript | Goldsky Mirror |
| Нужен готовый GraphQL API для фронтенда | Классический субграф |

## Плюсы и минусы Goldsky
| Плюсы | Минусы |
|---|---|
| Полная совместимость с существующими субграфами The Graph — низкий порог перехода | Managed-сервис — платная подписка, нет полного self-host контроля инфраструктуры |
| Mirror закрывает нишу "сырых данных в SQL" без написания обработчиков | Meньшее сообщество и меньше готовых примеров, чем у The Graph |
| Часто быстрее синхронизируется, чем публичная сеть The Graph | Зависимость от конкретного SaaS-провайдера (vendor lock-in) |
