# Практика: деплой и обновление контракта

## Почему в апгрейдных контрактах нельзя использовать обычный constructor
Конструктор выполняется **один раз, во время деплоя контракта реализации**, и его код исполняется в storage именно этого контракта реализации, а не прокси — потому что на момент выполнения конструктора прокси ещё физически не связан с реализацией через `delegatecall` (прокси в принципе не выполняет байт-код деплоя реализации). Значит, любая инициализация через обычный `constructor` запишет данные не туда, где их потом будет читать прокси.

**Решение — паттерн `initializer`:** вместо конструктора пишется обычная функция (`initialize()`), которую вызывают **один раз, сразу после присоединения прокси к реализации** — уже через `delegatecall`, то есть в правильном контексте storage:

```solidity
import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";
import "@openzeppelin/contracts-upgradeable/access/OwnableUpgradeable.sol";

contract MyLogicV1 is Initializable, OwnableUpgradeable, UUPSUpgradeable {
    uint256 public counter;

    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();   // защита от инициализации самой реализации напрямую (см. ниже)
    }

    function initialize(address initialOwner) public initializer {
        __Ownable_init(initialOwner);
        __UUPSUpgradeable_init();
        counter = 0;
    }

    function _authorizeUpgrade(address) internal override onlyOwner {}
}
```
Модификатор `initializer` (из `Initializable`) гарантирует, что функция может быть вызвана **только один раз** — повторный вызов приведёт к revert. Это критично: без такой защиты кто угодно мог бы вызвать `initialize()` повторно и, например, переназначить себя владельцем контракта.

**`_disableInitializers()` в конструкторе** — отдельная, легко упускаемая деталь: сам контракт **реализации** (не прокси!) тоже технически деплоится в блокчейн по собственному адресу и теоретически кто угодно может вызвать его `initialize()` напрямую, минуя прокси, и стать "владельцем" бесполезной пустой копии логики. Это не угрожает основному прокси, но считается плохой практикой и потенциальным вектором фишинга (пользователь может перепутать адрес реализации с адресом прокси). `_disableInitializers()` намеренно "сжигает" возможность инициализации именно для экземпляра-реализации при его собственном деплое.

## Деплой через OpenZeppelin Upgrades (Hardhat)
Ручной деплой прокси + правильная настройка слотов — источник ошибок, поэтому на практике почти всегда используют готовый тулинг, а не пишут прокси-контракт вручную:

```bash
npm install --save-dev @openzeppelin/hardhat-upgrades
```
```javascript
// scripts/deploy.js
const { ethers, upgrades } = require("hardhat");

async function main() {
  const MyLogicV1 = await ethers.getContractFactory("MyLogicV1");

  // деплоит и реализацию, и прокси, и сразу вызывает initialize()
  const proxy = await upgrades.deployProxy(MyLogicV1, [/* аргументы initialize() */], {
    kind: "uups",   // или "transparent"
  });
  await proxy.waitForDeployment();

  console.log("Адрес прокси (не меняется между апгрейдами):", await proxy.getAddress());
}
main();
```

## Обновление на новую версию
```javascript
// scripts/upgrade.js
const { ethers, upgrades } = require("hardhat");

async function main() {
  const PROXY_ADDRESS = "0x...";   // тот же адрес, что был при первом деплое
  const MyLogicV2 = await ethers.getContractFactory("MyLogicV2");

  // плагин сам проверяет совместимость storage layout между V1 и V2
  const upgraded = await upgrades.upgradeProxy(PROXY_ADDRESS, MyLogicV2);
  console.log("Обновлено, адрес прокси не изменился:", await upgraded.getAddress());
}
main();
```
Если в `MyLogicV2` нарушен порядок/типы унаследованных переменных (см. файл 02) — плагин **откажется** проводить апгрейд с понятной ошибкой, вместо того чтобы задеплоить контракт, который сломает данные пользователей в проде.

## Кто должен иметь право на апгрейд — практические рекомендации
Право вызвать `upgradeTo` — по сути, право заменить всю бизнес-логику контракта целиком, включая логику доступа к средствам пользователей. Это самая чувствительная функция во всей системе, и на защите проекта (модуль Г, файл про уязвимости) стоит явно показать, как она защищена:
- **Не оставлять на одном обычном приватном ключе** — компрометация этого одного ключа означает полный контроль над контрактом.
- **Мультиподпись (Gnosis Safe и подобные)** — апгрейд требует подписи нескольких доверенных участников, а не одного.
- **Timelock (задержка вступления в силу)** — апгрейд назначается заранее и вступает в силу только через объявленный срок (например, 48 часов), за которые пользователи и внешние наблюдатели успевают заметить готовящееся изменение и, если нужно, вывести средства или поднять тревогу до того, как новая логика начнёт действовать.
- **Постепенный переход к DAO-управлению** — право на апгрейд может со временем передаваться от команды разработки к держателям токена управления через голосование, что явно демонстрирует прогрессирующую децентрализацию проекта.

## Чек-лист перед апгрейдом в продакшене
- [ ] Новая реализация прошла через автоматическую проверку совместимости storage layout (плагин OZ Upgrades, а не ручной деплой)
- [ ] Право вызвать апгрейд не находится на одном обычном приватном ключе
- [ ] Есть задержка (timelock) между объявлением апгрейда и его вступлением в силу
- [ ] Проведён аудит/ревью именно diff между старой и новой реализацией, а не только новой версии в отрыве от контекста
- [ ] Explicitly проверено, что `initializer` не может быть вызван повторно, а конструктор реализации вызывает `_disableInitializers()`
