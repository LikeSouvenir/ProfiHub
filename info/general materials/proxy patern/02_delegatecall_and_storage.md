# Как это работает технически: delegatecall и хранение состояния

## delegatecall — механизм, на котором держится вся идея
В Solidity есть низкоуровневый способ вызвать код другого контракта — `call`. Но у обычного `call` контекст исполнения (в частности, **storage**, к которому обращается выполняемый код) — это storage **вызываемого** контракта. Для proxy-паттерна это не подходит: нам нужно, чтобы код исполнялся "чужой" (из implementation), а изменения применялись к storage "своего" (proxy) контракта.

Именно для этого существует **`delegatecall`**: он выполняет код другого контракта **в контексте вызывающего** — то есть implementation.sol физически исполняется, но любое обращение к `storage` (чтение/запись переменных), `msg.sender`, `msg.value` относится к **прокси**, а не к контракту реализации.

```solidity
// Максимально упрощённый прокси — только чтобы показать идею
contract SimpleProxy {
    address public implementation;

    constructor(address _implementation) {
        implementation = _implementation;
    }

    fallback() external payable {
        address impl = implementation;
        assembly {
            calldatacopy(0, 0, calldatasize())
            let result := delegatecall(gas(), impl, 0, calldatasize(), 0, 0)
            returndatacopy(0, 0, returndatasize())
            switch result
            case 0 { revert(0, returndatasize()) }
            default { return(0, returndatasize()) }
        }
    }
}
```
`fallback()` срабатывает на любой вызов, для которого в прокси нет отдельной явной функции — то есть буквально на всё, ведь у прокси и не должно быть своих бизнес-методов. Ассемблерный блок вручную копирует входящие calldata, делает `delegatecall` в implementation и пробрасывает результат обратно вызывающему — с точки зрения внешнего наблюдателя вызов выглядит так, будто он обратился напрямую к функции бизнес-логики, хотя физически весь вызов прошёл через прокси.

## Главная опасность: коллизия слотов хранения (storage collision)
Раз `delegatecall` исполняет чужой код над **своим** storage — переменные в прокси и в implementation должны использовать **одинаковые слоты хранения**, иначе implementation начнёт писать не туда, куда рассчитывал программист, затирая чужие данные.

Проблема конкретно: у прокси, как в примере выше, есть своя переменная `implementation` (адрес текущей логики) — она попадает в слот `0` storage. Если в контракте бизнес-логики первая объявленная переменная — например, `owner` — она **тоже** попадёт в слот `0` при компиляции implementation.sol как отдельного контракта. При вызове через `delegatecall` запись в `owner` физически перезапишет `implementation` — прокси начнёт указывать на случайный "адрес", в лучшем случае сломав контракт, в худшем — открыв уязвимость.

## Решение: EIP-1967 — стандартизированные слоты для служебных данных прокси
Вместо слота `0` (который легко случайно пересечётся с первой переменной логики) EIP-1967 определяет **псевдослучайные**, специально вычисленные слоты для служебной информации самого прокси — адреса реализации, администратора и бикона. Формула:

```solidity
// implementation slot = keccak256("eip1967.proxy.implementation") - 1
bytes32 constant IMPLEMENTATION_SLOT =
    0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc;

// admin slot = keccak256("eip1967.proxy.admin") - 1
bytes32 constant ADMIN_SLOT =
    0xb53127684a568b3173ae13b9f8a6016e243e63b6e8ee1178d6a717850b5d6103;

// beacon slot = keccak256("eip1967.proxy.beacon") - 1
bytes32 constant BEACON_SLOT =
    0xa3f0ad74e5423aebfd80d3ef4346578335a9a72aeaee59ff6cb3582b35133d50;
```
Вычитание `- 1` от хэша — намеренный трюк: получившееся число становится "нечитаемым" как обратный хэш известного значения (это защита от коллизии, а не просто произвольное значение). Вероятность, что переменная бизнес-логики случайно (через компиляцию по порядку объявления или через хэш ключа в `mapping`) попадёт ровно в этот слот, астрономически мала.

```solidity
function _getImplementation() internal view returns (address impl) {
    assembly {
        impl := sload(IMPLEMENTATION_SLOT)
    }
}
```
Благодаря такому подходу прокси может хранить свои служебные данные, вообще не пересекаясь с первым слотом переменных implementation — контракт логики может начинать объявлять свои переменные с обычного слота `0`, как любой другой контракт, ничего специально не зная о прокси, который будет им управлять.

## Вторая опасность: несовместимость layout между версиями
При обновлении на новую версию implementation порядок и типы объявленных переменных **нельзя менять произвольно** — можно только **добавлять новые переменные в конец**, не трогая и не переставляя местами старые. Если в v2 удалить или переставить переменную из v1, все данные, записанные при v1, "съедут" и будут интерпретированы неправильно.

```solidity
// v1
contract LogicV1 {
    uint256 public counter;      // слот 0
    address public owner;         // слот 1
}

// v2 — ПРАВИЛЬНО: новые переменные добавлены в конец
contract LogicV2 {
    uint256 public counter;      // слот 0 — не тронут
    address public owner;         // слот 1 — не тронут
    uint256 public newFeature;    // слот 2 — новая переменная, безопасно
}

// v2 — НЕПРАВИЛЬНО: переменные переставлены местами
contract LogicV2Broken {
    address public owner;         // теперь слот 0 — но там физически лежат старые данные counter!
    uint256 public counter;       // теперь слот 1 — а там лежит старый owner!
}
```
Инструменты вроде плагина OpenZeppelin Upgrades (`@openzeppelin/hardhat-upgrades`) автоматически проверяют совместимость layout при каждом деплое новой версии и не дадут задеплоить контракт, ломающий порядок хранения — на практике почти всегда стоит полагаться на такую автоматическую проверку, а не отслеживать это вручную.
