# Виды прокси-паттернов: Transparent, UUPS, Beacon, Diamond

Все реализации ниже используют один и тот же фундамент — `delegatecall` и стандартизированные слоты EIP-1967 (файл 02). Разница между ними — **где хранится логика обновления** и **как маршрутизируются вызовы**. Выбор конкретного паттерна — это ответ на два практических вопроса: кто может обновлять контракт и как дёшево обходится каждый обычный вызов.

## Transparent Proxy
Исторически первый широко принятый паттерн (реализация OpenZeppelin — `TransparentUpgradeableProxy`).

**Идея разделения ролей:** прокси сам решает, кому какой вызов направить, основываясь на том, **кто** вызывает — администратор или обычный пользователь:
- Если вызывающий — **администратор апгрейда**, вызов маршрутизируется на служебные функции самого прокси (`upgradeTo`, `changeAdmin` и т.п.).
- Если вызывающий — **любой другой адрес**, вызов идёт через `delegatecall` в контракт реализации, как обычный бизнес-вызов.

```solidity
// Упрощённая логика внутри TransparentUpgradeableProxy
function _fallback() internal {
    if (msg.sender == _getAdmin()) {
        // административные функции прокси — upgradeTo, changeAdmin...
    } else {
        _delegate(_implementation());
    }
}
```

**Зачем такое разделение — проблема коллизии селекторов функций.** Если бы прокси не делал эту проверку, а у контракта реализации случайно оказалась бы функция с тем же 4-байтовым селектором, что и `upgradeTo(address)` прокси, — вызов мог бы уйти не туда, куда рассчитывал вызывающий (например, обычный пользователь случайно вызвал бы административную функцию апгрейда вместо бизнес-метода реализации с похожим селектором). Проверка "кто вызывает" снимает эту неоднозначность.

**Практическая деталь:** права администратора обычно не хранят на обычном EOA-адресе (кошельке), а выносят в отдельный служебный контракт `ProxyAdmin`, которым, в свою очередь, управляет мультиподпись или DAO — это добавляет ещё один уровень контроля доступа к самой важной операции системы.

**Минусы:** дороже по газу на **каждый** обычный вызов (лишняя проверка `msg.sender == admin` на каждый вызов, даже не административный), больше байт-кода самого прокси.

## UUPS (Universal Upgradeable Proxy Standard, EIP-1822)
Идея переворачивает Transparent Proxy: логика апгрейда переносится **из прокси в саму реализацию**.

```solidity
import "@openzeppelin/contracts-upgradeable/proxy/utils/UUPSUpgradeable.sol";

contract MyLogicV1 is UUPSUpgradeable {
    function _authorizeUpgrade(address newImplementation)
        internal
        override
        onlyOwner   // здесь и определяется, кто имеет право на апгрейд
    {}

    // ...остальная бизнес-логика
}
```
Сам прокси при этом становится минимальным — просто `delegatecall` во всех случаях, без встроенной проверки на администратора, поэтому **обычные вызовы стоят дешевле газа**, чем в Transparent Proxy. Функция `upgradeTo` физически находится в коде реализации (унаследована от `UUPSUpgradeable`) и вызывается через тот же `delegatecall`, поэтому изменяет она именно storage прокси — то есть implementation-контракт сам умеет "переключить себя" на новую версию.

**Главный риск UUPS:** если в новой версии реализации разработчик забудет унаследовать `UUPSUpgradeable` (или иначе уберёт функцию апгрейда) — контракт **навсегда** потеряет возможность обновляться, потому что логика апгрейда живёт именно в реализации, а не в прокси. Это называется **"заблокировать" (brick) контракт**. Плагин OpenZeppelin Upgrades при деплое автоматически проверяет, что новая реализация по-прежнему содержит корректную логику апгрейда — использование этого инструмента, а не ручного деплоя, снижает риск такой ошибки почти до нуля.

**На сегодня UUPS — рекомендация OpenZeppelin по умолчанию** для большинства новых проектов, именно из-за более низкой стоимости обычных вызовов — плата за это чуть более высокая ответственность разработчика новой версии за то, чтобы не "потерять" логику апгрейда.

## Beacon Proxy
Решает другую задачу: что делать, если у вас **много одинаковых прокси**, которые все должны обновляться **одновременно, одной транзакцией** — например, фабрика, которая по запросу пользователей деплоит десятки/сотни лёгких прокси-кошельков или NFT-коллекций с одинаковой логикой.

**Архитектура:**
```
Proxy 1 ──┐
Proxy 2 ──┼──►  UpgradeableBeacon  ──►  Implementation
Proxy 3 ──┘        (хранит адрес
                     текущей логики)
```
Каждый отдельный прокси не хранит адрес реализации напрямую — вместо этого в его `beacon`-слоте (EIP-1967) лежит адрес контракта-бикона (`UpgradeableBeacon`), а уже бикон хранит актуальный адрес реализации. Обновление логики — это **одна** транзакция на контракт бикона (`beacon.upgradeTo(newImplementation)`), и она мгновенно меняет поведение **всех** прокси, ссылающихся на этот бикон, без необходимости обновлять каждый из них по отдельности.

**Когда выбирать Beacon:** любой сценарий фабрики (много однотипных экземпляров контракта на пользователя/сущность), где важно централизованно управлять апгрейдом сразу всех экземпляров. Для одного отдельного контракта с уникальной логикой Beacon избыточен — тут достаточно Transparent или UUPS.

## Diamond (EIP-2535) — кратко
Более сложный паттерн для больших систем: вместо одного контракта реализации логика разбивается на несколько независимых контрактов-**фасетов (facets)**, каждый отвечает за свою группу функций. Прокси ("diamond") хранит таблицу соответствия "селектор функции → адрес фасета" и при вызове делает `delegatecall` в нужный фасет по этой таблице.

**Зачем это нужно, если уже есть UUPS/Transparent:**
- Обходит лимит размера контракта в EVM (24 КБ байт-кода) — логику можно дробить на сколько угодно фасетов.
- Позволяет обновлять/добавлять/удалять **отдельные функции**, а не заменять всю реализацию целиком, как в других паттернах.

**Цена этой гибкости** — существенно более высокая сложность архитектуры, аудита и тестирования, поэтому Diamond обычно оправдан только для действительно крупных систем (протоколы уровня целых DeFi-платформ), а не для типичного хакатонного/учебного проекта.

## Итоговая сравнительная таблица
| Паттерн | Где живёт логика апгрейда | Газ на обычный вызов | Риск "заблокировать" контракт | Когда выбирать |
|---|---|---|---|---|
| Transparent Proxy | В прокси | Выше (проверка admin на каждый вызов) | Низкий | Нужна максимальная предсказуемость и разделение ролей "из коробки" |
| UUPS | В реализации | Ниже | Есть, но снимается тулингом OZ | Рекомендация по умолчанию для новых проектов |
| Beacon | В отдельном контракте-биконе | Такой же, как у выбранной базовой реализации (обычно UUPS/Transparent поверх) | Низкий | Много однотипных прокси, которые должны обновляться синхронно |
| Diamond | В таблице селекторов + фасетах | Немного выше (доп. lookup по таблице) | Средний (сложнее логика) | Очень крупные системы, упирающиеся в лимит размера контракта |
