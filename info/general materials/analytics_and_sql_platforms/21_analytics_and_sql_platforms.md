# Аналитика и SQL по ончейн-данным: Dune, Flipside, Footprint, Allium

## Это не то же самое, что слой индексации для фронтенда
В `19_goldsky_indexing.md` разбирался слой индексации (субграфы, Mirror) — его задача дать **приложению** быстрый, предсказуемый, машиночитаемый доступ к структурированным данным: GraphQL-эндпоинт или строка в своей базе, на которые опирается интерфейс продукта. Аналитические SQL-платформы решают **другую** задачу: дать **человеку-аналитику** удобный интерфейс, чтобы исследовать ончейн-данные произвольными запросами, строить дашборды и делиться выводами — не для того, чтобы на этих запросах работал продакшен-фронтенд.

Разница принципиальна и стоит того, чтобы явно её проговорить:

| | Индексатор (субграф/Mirror) | Аналитическая SQL-платформа (Dune и подобные) |
|---|---|---|
| Кто основной потребитель | Код (фронтенд, бэкенд) | Человек (аналитик, исследователь, комьюнити-менеджер) |
| Схема данных | Фиксируется заранее под конкретный контракт/сценарий | Произвольная — можно написать любой SQL-запрос к общей базе |
| Формат ответа | GraphQL API / строка в вашей БД, оптимизировано под многократные однотипные запросы | Результат SQL-запроса, дашборд, экспорт CSV |
| Задержка и предсказуемость | Sub-second, гарантированный SLA для продакшена | Query-on-demand — запрос выполняется по требованию, время ответа не гарантировано и не рассчитано на встраивание в UI с высокой нагрузкой |
| Типичная модель тарификации | Плата за инфраструктуру/трафик API | Кредиты за выполнение запроса, часто с лимитом на бесплатном тарифе |

## Dune Analytics — самый известный SQL-native инструмент
**Архитектура:** Dune — это хостед data warehouse с SQL-редактором поверх (исторически на PostgreSQL, с 2024 года — движок на базе Trino). Данные организованы в два слоя:
- **Raw-таблицы** — зеркало того, что отдаёт нода: `ethereum.transactions`, `ethereum.blocks`, `ethereum.logs`, `ethereum.traces`. Работают для любого контракта в сети, но события в них не декодированы — нужно самостоятельно разбирать сырые логи.
- **Decoded-таблицы** — результат работы **spellbook**: когда контракт верифицирован и добавлен, каждое его событие становится отдельной, уже читаемой таблицей вида `uniswap_v3_ethereum.Factory_evt_PoolCreated` или `aave_v3_ethereum.Pool_evt_Borrow`.

**Spellbook — ключевая архитектурная деталь:** это открытый **dbt-проект** — слой SQL-трансформаций, где каждая "спелла" (spell) — это SQL-запрос, декларативно описывающий, как превратить сырые/декодированные данные в чистый, готовый к анализу датасет. Исторически спеллбук наполнялся сообществом (кто угодно мог прислать pull request с новой моделью), сейчас Dune принимает вклад более выборочно, но сама модель "SQL-трансформации как открытый, версионируемый код" сохраняется.

**Практические свойства:**
- Покрытие **100+ сетей**, не только EVM — включая Solana, Bitcoin и другие архитектуры.
- Огромная база уже написанных публичных запросов и дашбордов — типовая метрика популярного протокола почти наверняка уже кем-то посчитана, можно форкнуть чужой запрос вместо написания с нуля.
- Есть встроенный AI-помощник, который умеет писать SQL по запросу на естественном языке — снижает порог входа для тех, кто SQL не знает.
- Есть **Query API** для программного получения результатов сохранённого запроса — но это именно API для выгрузки результата аналитического запроса по запросу клиента, а не низколатентный слой под нагрузку живого продукта: лимиты кредитов и отсутствие гарантий по задержке делают его непригодным как замену индексатору для фронтенда — привязка к живому интерфейсу с большим потоком пользовательских запросов быстро упрётся и в стоимость, и в задержку.

## Flipside Crypto — курируемые данные и SQL-бонусы
Похожая на Dune SQL-модель (тоже пишете запросы и строите дашборды), но с другим акцентом:
- **Курируемые, заранее очищенные таблицы** в стиле Snowflake, а не сырые данные "как есть" — меньше ручной работы по декодированию/нормализации по сравнению с raw-таблицами Dune.
- **Масштабная классификация кошельков** — сотни миллионов адресов помечены по типу/поведению, что снимает с аналитика значительную часть работы по сегментации пользователей.
- **AI-инструменты и автоматизация поверх аналитики** — не только написание SQL, но и автоматические оповещения/скоринг.
- Исторически у Flipside была программа денежных вознаграждений за полезные аналитические запросы от сообщества (bounty-модель) — способ быстро нарастить библиотеку готовых дашбордов силами независимых аналитиков.

**Когда выбирать Flipside вместо Dune:** если важнее готовые, уже нормализованные данные и меньше времени тратить на самостоятельную очистку/декодирование, особенно для задач, завязанных на поведение и классификацию кошельков.

## Footprint Analytics — акцент на no-code и готовые бизнес-метрики
Отличие от двух предыдущих — не только SQL-редактор, но и **конструктор дашбордов без кода** (drag-and-drop) для тех, кому не нужно/не хочется писать запросы вручную. Вторая отличительная черта — **таблицы с уже посчитанными бизнес-метриками**, а не только сырые/декодированные данные: например, метрики вроде wash trading для NFT-рынков доступны как готовое поле, а не результат, который аналитику пришлось бы самостоятельно выводить сложным запросом. Это удобно для быстрых обзорных дашбордов и презентаций, но менее гибко, если нужен нестандартный, глубоко кастомный анализ.

## Allium — не дашборд, а корпоративный слой данных
Allium принципиально другого класса — это не инструмент для быстрого исследования силами одного аналитика, а **инфраструктура данных для компаний** (биржи, комплаенс-команды, финтех-продукты на ончейн-данных):
- Забирает сырые данные из **150+ сетей** и стандартизирует их в предметные "вертикали" — например, отдельный нормализованный слой данных по стейблкоинам (выпуск, погашение, переводы), по RWA, по лендингу, по стейкингу — единообразно, независимо от того, из какого протокола/сети пришли исходные события.
- **Два режима доставки данных**, а не только "зайти на сайт и посмотреть дашборд": **pull** (REST API, SQL-запросы к managed-инфраструктуре) и **push** (потоковая доставка через Kafka, Google Pub/Sub, SNS) — то есть Allium может быть источником для собственного бэкенда компании в режиме, близком к реальному времени, а не только инструментом разового исследования.
- Прямая выгрузка в собственное корпоративное хранилище — Snowflake, BigQuery, Databricks — то есть данные физически попадают в инфраструктуру заказчика, а не остаются доступны только через чужой веб-интерфейс.

**Когда выбирать Allium вместо Dune/Flipside/Footprint:** когда данные нужны не аналитику для разового исследования, а production-системе компании — комплаенсу, риск-скорингу, встроенной в продукт аналитике, требующей контролируемой задержки и собственного владения данными.

## Сводная таблица: кто для чего
| Платформа | Основная аудитория | Модель данных | Сильная сторона |
|---|---|---|---|
| **Dune** | Аналитики, комьюнити, исследователи | Raw + decoded (spellbook/dbt) | Максимальный охват сетей и готовых запросов, открытая модель трансформаций |
| **Flipside** | Аналитики, DeFi/growth-команды | Курируемые, заранее очищенные таблицы | Меньше ручной очистки, сильная классификация кошельков |
| **Footprint** | Аналитики без глубокого SQL, маркетинг/презентации | Raw/decoded + готовые бизнес-метрики | No-code дашборды, посчитанные метрики "из коробки" |
| **Allium** | Компании: комплаенс, биржи, встроенная в продукт аналитика | Стандартизированные предметные вертикали | Push-доставка, выгрузка в собственный warehouse, масштаб |

## Почему это действительно не замена индексатору — если коротко
1. **Модель тарификации и задержки не рассчитана на трафик живого продукта.** Query-on-demand с кредитами за запрос — это нормально, когда аналитик раз в день смотрит на дашборд, и неприемлемо, когда каждый визит пользователя в ваше приложение должен породить SQL-запрос к чужой платформе.
2. **Нет GraphQL/API, спроектированного под конкретную форму данных вашего фронтенда.** Субграф отдаёт ровно ту сущность и в той форме, которая нужна компоненту интерфейса. Результат SQL-запроса на аналитической платформе — это таблица общего назначения, которую ещё нужно адаптировать под нужды конкретного экрана.
3. **Разное назначение по природе.** Индексатор отвечает на вопрос "что показать этому конкретному пользователю прямо сейчас" — аналитическая платформа отвечает на вопрос "что вообще происходит в протоколе/экосистеме" — это разные классы вопросов, и вторые плохо переиспользуются как ответ на первые.

**Практический вывод:** для дашборда комьюнити-менеджера, внутренней отчётности команды или разового исследования — Dune/Flipside/Footprint отлично подходят и не требуют собственной инфраструктуры. Для того, чтобы фронтенд продукта показывал пользователю данные в реальном времени, — нужен слой индексации (`19_goldsky_indexing.md`) или, для промышленного масштаба данных под свой бэкенд, — потоковая доставка уровня Allium.

## Как это подать на защите проекта (модуль Г)
Если в архитектуре проекта есть и продуктовый фронтенд, и внутренняя аналитика/отчётность — сильный ответ на вопрос "как вы работаете с данными" явно разделяет эти два слоя: индексатор/субграф под интерфейс продукта, и отдельно — SQL-дашборд (даже нарисованный на Dune за 20 минут) под метрики для себя и инвесторов. Смешивание этих двух ролей в один инструмент — типичная ошибка, которая выдаёт поверхностное понимание архитектуры данных.

## Вопросы для самопроверки
1. Почему Query API Dune не годится как основной источник данных для высоконагруженного фронтенда, даже если технически он может вернуть нужные данные?
2. В чём разница между raw-таблицами и decoded-таблицами в Dune, и какую роль в этом различии играет spellbook?
3. Чем модель данных Flipside (курируемые таблицы) отличается от подхода Dune (raw + community-decoded), и какой ценой достигается эта разница?
4. Почему Allium описывают как "не дашборд, а слой данных" — какие два режима доставки это подчёркивают?
5. Приведите пример проекта, где нужны одновременно и субграф/индексатор, и SQL-аналитическая платформа — объясните, какую роль играет каждый из инструментов.
