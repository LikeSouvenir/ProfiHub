# Зачем нужен индексатор и при чём тут Envio

## Проблема: блокчейн — плохая база данных для чтения

Смарт-контракт умеет отдавать текущее состояние через `view`-функции, но не умеет отвечать на вопросы вида:

- «покажи все переводы этого пользователя за последний месяц»
- «отсортируй пулы по объёму торгов»
- «сколько всего заданий добавлено, сгруппируй по авторам»

Единственный штатный способ получить историю — перебирать логи через JSON-RPC (`eth_getLogs`) блок за блоком. На реальной сети это означает десятки тысяч запросов и часы ожидания.

**Пример из практики.** Чтобы собрать историю событий одного контракта с момента деплоя, фронтенду пришлось бы:

```js
// Наивный подход: цикл по диапазонам блоков
for (let from = startBlock; from < latestBlock; from += 2000) {
    const logs = await provider.getLogs({
        address: CONTRACT_ADDRESS,
        fromBlock: from,
        toBlock: from + 2000,
    });
    // ...декодировать, сложить, посчитать
}
```

Провайдеры ограничивают размер диапазона (обычно 2000–10000 блоков), поэтому для истории в 20 млн блоков получится около 10 тысяч последовательных запросов. Делать это при каждой загрузке страницы невозможно.

## Решение: индексатор

**Индексатор** — сервис, который один раз прочитывает блокчейн, раскладывает события в обычную БД (Postgres) и отдаёт их фронтенду через GraphQL. Дальше приложение работает с нормальной базой: фильтры, сортировки, агрегации, пагинация.

Схема:

```
Блокчейн  →  Индексатор  →  Postgres  →  GraphQL API  →  React-приложение
(события)    (обработчики)   (сущности)   (запросы)
```

Индексатор состоит из трёх частей, и они одинаковы у всех решений на рынке:

1. **Конфигурация** — какие контракты, на каких сетях и какие события читать.
2. **Схема данных** — какие сущности (таблицы) получатся на выходе.
3. **Обработчики событий** — код, который превращает событие в запись в БД.

## Место Envio среди других индексаторов

| Решение | Язык обработчиков | Особенность |
|---|---|---|
| **The Graph** | AssemblyScript | Первопроходец, децентрализованная сеть, огромная библиотека готовых субграфов |
| **Envio** | TypeScript | Самый быстрый по бенчмаркам за счёт HyperSync, self-host через Docker |
| **Ponder** | TypeScript | Лёгкий, полностью TS, синхронизация через RPC |
| **Subsquid / SQD** | TypeScript | Упор на тяжёлый ETL и SQL-агрегации |
| **Goldsky** | AssemblyScript | Managed-хостинг субграфов The Graph + стриминг в Postgres |

Envio решает конкретную боль — **скорость первичной синхронизации** (backfill). Обычный индексатор на RPC читает историю часами; Envio делает это за минуты, потому что вместо JSON-RPC использует собственный движок доступа к данным HyperSync.

## Два продукта Envio

Важно не путать два разных инструмента с похожими названиями:

- **HyperSync** — низкоуровневый движок доступа к данным. Замена RPC: отдаёт сырые логи, транзакции и блоки. Нужен, когда вы строите свой конвейер обработки.
- **HyperIndex** — полноценный фреймворк индексации, построенный **поверх** HyperSync. Даёт схему, обработчики, Postgres и GraphQL из коробки.

Для типового приложения нужен HyperIndex. HyperSync берут, когда нужны сырые данные на максимальной скорости — например, для аналитики или собственного ETL.
