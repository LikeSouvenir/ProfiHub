# Chainlink: платформа, а не один продукт

Chainlink — старейшая и наиболее широко интегрированная оракульная сеть; важно понимать, что это не один продукт «дать контракту цену», а набор связанных сервисов, построенных на общей инфраструктуре децентрализованных сетей узлов (**DON — Decentralized Oracle Network**).

## Data Feeds — классические push-оракулы
Данные о ценах (и других показателях) забираются множеством независимых операторов узлов из разных источников, агрегируются через протокол внесетевого консенсуса (**OCR — Off-Chain Reporting**: узлы согласуют единое значение off-chain, подписывают его совместно, и в контракт уходит только одна финальная транзакция вместо N отдельных от каждого узла — заметно дешевле по газу, чем если бы каждый узел писал своё значение отдельно) и публикуются в контракт по push-модели:
- **Heartbeat** — гарантированное обновление не реже, чем раз в заданный интервал, даже если цена не менялась.
- **Deviation threshold** — досрочное обновление, если значение изменилось больше, чем на заданный процент.

**Пример входа в лендинг-протокол:** контракт, принимающий wrapped BTC как залог, не может полагаться на цену из одного DEX-пула (её можно временно сдвинуть манипуляцией ликвидности прямо перед транзакцией) — вместо этого он читает уже агрегированное на множестве источников значение из Chainlink Data Feed, которое одной ликвидностью с одного пула сдвинуть не получится.

**Data Streams** — более новый, высокочастотный вариант той же идеи, ориентированный на pull-доставку с низкой задержкой для приложений, которым нужна более свежая цена, чем даёт стандартный heartbeat-цикл (торговые платформы, где значение важно именно «прямо сейчас», а не «недавно»).

## Chainlink Functions — произвольные off-chain вычисления
Позволяет контракту запросить исполнение **произвольного кода** (обращение к любому API, сложные вычисления) в защищённой off-chain среде сети узлов, и получить обратно в контракт уже готовый, верифицированный результат.

**Когда это нужно, а не просто Data Feeds:** Data Feeds отвечают только на заранее известные, стандартизированные вопросы («какая сейчас цена X»). Functions нужен, когда данные не укладываются в готовый фид — например, обратиться к внутреннему API логистической компании и получить статус конкретной посылки, или посчитать нестандартную агрегацию из нескольких источников на лету. Отдельная показательная область применения — **RWA (реальные активы)**: если авторитетная запись о состоянии актива (например, текущий статус обслуживания кредита) всё ещё физически живёт в обычной базе данных, а не в блокчейн-нативном фиде, Functions — способ подтянуть именно эти конкретные данные по запросу, не дожидаясь появления готового стандартного фида под каждый частный случай.

## Chainlink Automation — децентрализованные «сторожа» (keepers)
Решает задачу «кто вызовет функцию контракта, если событие произошло, а людей рядом с кнопкой может не оказаться»: сеть узлов постоянно проверяет заданные условия (наступило ли время, выполнилось ли условие в контракте) и **сама** отправляет транзакцию вызова нужной функции, когда условие срабатывает.

**Типичные сценарии:** автоматическая ликвидация недообеспеченной позиции в лендинг-протоколе, ребалансировка индекса по расписанию, автоматическое исполнение отложенного платежа, начисление процентов/наград без ручного триггера пользователем.

## CCIP — кросс-чейн-сообщения на той же инфраструктуре
Отдельно подробно разобран в `17_bridges_and_messaging.md` как один из протоколов кросс-чейн-мессенджинга — здесь важно зафиксировать архитектурную связь: CCIP не отдельный продукт «с нуля», а **расширение** той же оракульной инфраструктуры (DON) на задачу передачи сообщений и токенов между сетями, с добавленной отдельной независимой сетью мониторинга (**Risk Management Network**), которая параллельно следит за аномалиями (например, попытку «бесконечной эмиссии» токена при межсетевом переводе) и может экстренно остановить операцию.

## Почему это описывают как «платформенный ров» (moat)
Один и тот же проект типично использует сразу несколько продуктов Chainlink вместе: Data Feeds — для оценки стоимости, Automation — чтобы триггерить сделку по условию, CCIP — чтобы рассчитаться в другой сети. Это не совпадение, а осознанная архитектурная стратегия Chainlink — продукты специально спроектированы так, чтобы комбинироваться поверх одной инфраструктуры, что снижает стоимость интеграции каждого следующего сервиса для команды, уже использующей хотя бы один из них.

## Итоговая таблица продуктов
| Продукт | Задача | Модель доставки |
|---|---|---|
| Data Feeds | Курсы/показатели, обновляемые постоянно | Push (heartbeat + deviation) |
| Data Streams | То же, но с более низкой задержкой | Pull, высокая частота |
| Functions | Произвольный off-chain код/API | По запросу, разовый вызов |
| Automation | Вызов функции по расписанию/условию | Push, инициировано сетью узлов, а не пользователем |
| CCIP | Сообщения и токены между сетями | Через ту же DON-инфраструктуру + отдельный слой мониторинга рисков |
