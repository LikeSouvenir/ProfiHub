# Выбор оракула: сравнение, безопасность, практика

## Сводная сравнительная таблица
| | Chainlink | Pyth | API3 | RedStone |
|---|---|---|---|---|
| Модель доставки | Push (Data Feeds) + pull (Data Streams) | Pull | Push | Гибрид push/pull |
| Источник данных | Третья сторона (операторы узлов) | Первая сторона (биржи/маркет-мейкеры) | Первая сторона (сам провайдер API через Airnode) | Смешанно |
| Где хранятся данные между обновлениями | On-chain storage | Off-chain, pull в момент нужды | On-chain storage | Off-chain (DDL), никогда не хранится в storage надолго |
| Типичная задержка обновления | Секунды–минуты (heartbeat/deviation) | Доли секунды – единицы секунд | Секунды–минуты | По требованию, настолько свежо, насколько взято из DDL |
| Помимо цен | Functions, Automation, CCIP, VRF | В основном данные (цены, в т.ч. экзотические классы активов) | dAPI + OEV Network | Модульная доставка под разные типы данных |
| Сильная сторона | Широчайший охват сетей и сопутствующих сервисов, «платформенный» подход | Максимальная свежесть, доверительный интервал | Прямая связь с источником без посредника, возврат OEV | Экономичность для длинного хвоста редко запрашиваемых активов |

## Как выбирать — вопросы по порядку
1. **Нужны ли контракту данные постоянно (лендинг, стейблкоин), или только в момент конкретного действия пользователя (открытие позиции, разовый расчёт)?** Постоянная потребность тянет к push (Chainlink Data Feeds, API3 dAPI); разовая, но критичная по свежести — к pull (Pyth, RedStone).
2. **Насколько критична миллисекундная свежесть данных прямо сейчас?** Высокочастотная торговля/деривативы — сильный аргумент за Pyth; классический лендинг-протокол вполне устроит push-модель с heartbeat в минуты.
3. **Нужны ли, помимо данных, ещё автоматизация или произвольные off-chain вычисления?** Если да — Chainlink Automation/Functions закрывают это без интеграции отдельного стороннего сервиса.
4. **Насколько нишевый актив/источник?** Для длинного хвоста редко запрашиваемых показателей экономичнее модель RedStone (платите только за фактическое использование), чем держать push-обновления для всех подряд.
5. **Важна ли прямая, прослеживаемая связь с конкретным источником данных без посредника?** Тогда стоит присмотреться к API3/Airnode — данные подписаны непосредственно тем, кто их создаёт.

## Оракул как поверхность атаки — на что смотреть архитектурно
Возвращаясь к тезису из файла 22 — оракул почти всегда стоит отдельно разбирать в контексте безопасности проекта. Конкретные архитектурные вопросы, которые стоит явно проговорить (в том числе на защите, модуль Г, файл 08):

- **Манипуляция тонким источником.** Если оракул (или хотя бы один из агрегируемых источников) берёт цену из низколиквидного рынка, её можно временно сдвинуть относительно небольшой сделкой — классический сценарий флэш-кредитной атаки на протоколы, полагавшиеся на цену одного DEX-пула вместо агрегированного оракула.
- **Устаревшие данные, использованные как актуальные (staleness).** Контракт обязан явно проверять `timestamp` полученного значения и отклонять operacию, если данные старше допустимого порога — а не молча использовать последнее известное значение, даже если оракул давно не обновлялся (например, из-за сбоя).
- **Единая точка отказа в модели доверия.** Полагаться на единственный источник/публикатора без агрегации нескольких независимых — то же архитектурное решение, что и «1 из 1» верификатор в мостах (`18_multichain_risks_governance.md`, инцидент Kelp DAO) — минимальный порог экономит на интеграции, но резко снижает отказоустойчивость.
- **Зависимость pull-модели от готовности инициировать запрос.** Если логика контракта предполагает, что кто-то обязательно вызовет функцию с приложенными свежими данными (Pyth/RedStone), стоит продумать, что произойдёт, если этого не случится вовремя — деградация должна быть предсказуемой (отказ выполнить действие), а не тихим использованием устаревшего значения.
- **Доверие к мосту при кросс-чейн-доставке.** Pyth передаёт данные через Wormhole — значит, риски модели доверия конкретно этого моста (файл 17) транзитивно становятся и риском вашего оракула на той сети, куда данные доставляются через него.

## Как подать эту тему на защите проекта (модуль Г)
Сильный ответ на вопрос «а как вы работаете с внешними данными» проговаривает цепочку: какой тип задачи (постоянный фид / разовый вызов / автоматизация) → почему выбрана именно push или pull модель под эту задачу → какая модель доверия к источнику (первая сторона / третья сторона / сколько независимых источников агрегируется) → что происходит в контракте при устаревших/недоступных данных. Это тот же уровень конкретики, который превращает общий тезис «мы используем Chainlink» в содержательное архитектурное решение — ровно то, что нужно для балла 3 по критериям обоснования технологий и уязвимостей.

2. В чём разница между push и pull моделью с точки зрения того, кто и когда платит газ за обновление данных?
3. Чем first-party источник данных архитектурно отличается от third-party, и какой компромисс каждый из них создаёт?
4. Почему RedStone описывают как гибрид push и pull, а не чисто одну из двух моделей?
5. Что такое OEV в контексте API3, и почему возврат этой ценности самому приложению — осмысленное архитектурное решение, а не просто маркетинговая деталь?
6. Приведите пример, где неправильная проверка свежести данных оракула (staleness check) могла бы привести к эксплуатации контракта, даже если сам оракул технически работал исправно.
