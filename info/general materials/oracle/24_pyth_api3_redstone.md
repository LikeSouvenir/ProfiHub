# Pyth, API3, RedStone: альтернативные архитектурные ставки

Все три решения ниже возникли как ответ на одну и ту же критику классической push-модели третьей стороны: посредники-операторы узлов добавляют лишнее звено доверия и задержку, а постоянная запись в storage тратит газ впустую, даже когда данные никто не читает между обновлениями. Каждый проект решает это по-своему.

## Pyth Network — first-party, pull, высокая частота
**Архитектурная ставка:** данные должны поступать напрямую от тех, кто их и создаёт — бирж и маркет-мейкеров, — а не через посредника, который сам забирает их из чужого API.

**Как устроено:**
1. **120+ поставщиков данных первой стороны** — не анонимные операторы узлов, а сами торгующие организации (крупные биржи, трейдинговые фирмы), которые публикуют собственные котировки напрямую.
2. Публикации стекаются на выделенный прикладной блокчейн **Pythnet**, где специальный алгоритм агрегирует все входящие цены в единое значение — причём не просто среднее, а значение **с доверительным интервалом (confidence interval)**, показывающим, насколько публикующие стороны согласны друг с другом в моменте — сам по себе полезный сигнал: широкий интервал говорит о повышенной неопределённости рынка прямо сейчас.
3. Агрегированные данные транслируются через мост **Wormhole** на поддерживаемые сети и лежат в off-chain кэширующем сервисе (**Hermes**).
4. Контракт-потребитель **сам** забирает свежую подписанную цену и прикладывает её к транзакции ровно в момент, когда она нужна (**pull**) — платит газ только за этот единственный акт использования, а не за постоянные обновления впрок.

**Компромисс, который стоит проговаривать явно:** pull-модель зависит от того, что кто-то реально инициирует получение данных в нужный момент — если по какой-то причине запрос не отправлен (сеть перегружена, мост Wormhole временно недоступен), у контракта в этот момент просто не окажется свежей цены, и его логике нужно быть готовой корректно обработать такой сбой (например, не выполнять операцию вместо того, чтобы использовать устаревшее значение).

**Где обычно выбирают Pyth:** приложения, для которых критична именно **свежесть** цены в моменте — бессрочные деривативы (perpetuals), маржинальная торговля, любые сценарии, где устаревшая на минуту цена — уже неприемлемый риск.

## API3 — first-party через Airnode, без сети посредников вообще
**Архитектурная ставка:** убрать посредника-оператора узла полностью, а не просто добавить к нему первую сторону как альтернативу — сам поставщик API разворачивает лёгкий узел **Airnode** и публикует данные с подписью собственным ключом напрямую.

**Как устроено:**
1. Поставщик данных (владелец обычного Web2 API) разворачивает **Airnode** — открытый, серверless-фреймворк, не требующий держать полноценную блокчейн-ноду или платить за стейкинг сетевого токена посредника.
2. Airnode подписывает данные напрямую ключом поставщика и публикует их on-chain — если контракту нужны данные ровно от одного конкретного источника, Airnode может обслуживать это без какой-либо дополнительной сети агрегации вообще.
3. Когда для одного показателя нужно несколько независимых источников (например, ETH/USD от нескольких Airnode-узлов сразу) — отдельные агрегирующие контракты собирают публикации нескольких Airnode в единое значение, отбрасывая выбросы.
4. Готовый агрегированный, непрерывно обновляемый показатель называется **dAPI (decentralized API)** — контракт просто читает его текущее on-chain значение.

**Отдельная деталь, характерная именно для API3 — OEV Network.** Момент обновления оракула — это момент, когда возникает **Oracle Extractable Value**: тот, кто узнаёт об обновлении цены первым и успевает среагировать (например, мгновенно ликвидировать позицию сразу после обновления), может извлечь из этого прибыль за счёт протокола. Вместо того чтобы отдавать эту ценность случайным образом стороннему боту, API3 организует для неё отдельный аукцион — right to update the feed продаётся тому, кто предложит больше, а вырученные средства возвращаются **самому приложению**, использующему dAPI, а не остаются у постороннего.

**Где обычно выбирают API3:** сценарии, где важна прямая, прослеживаемая связь «этот конкретный источник данных подписал именно это значение» (в том числе нишевые, некрупные источники, для которых нет смысла в отдельной сети посредников), и где ценно вернуть OEV-доход самому приложению, а не терять его в пользу стороннего наблюдателя.

## RedStone — модульная архитектура, данные вне storage
**Архитектурная ставка:** зачем вообще постоянно хранить данные в дорогом on-chain storage, если можно доставлять их прямо внутри транзакции, только когда они реально нужны — расширяя саму идею pull ещё на шаг дальше.

**Как устроено:**
1. Поставщики данных публикуют подписанные обновления в **Data Distribution Layer (DDL)** — децентрализованный кэширующий слой (построен поверх сети Streamr и хранения на базе Arweave), полностью **вне** блокчейна.
2. Когда пользователь отправляет транзакцию, которой нужны данные (например, открывает позицию с плечом), клиентская библиотека сама забирает свежие подписанные данные из DDL и **дописывает их в конец calldata** транзакции — данные физически едут вместе с вызовом, а не читаются из отдельного контракта.
3. Контракт-потребитель (унаследовавший специальный базовый контракт RedStone) **извлекает** данные прямо из calldata текущего вызова, проверяет подписи и свежесть — и тут же использует значение, ничего не записывая в постоянный storage.

**Ключевое архитектурное следствие:** оракул в принципе никогда не занимает отдельный постоянный слот storage под цену — данные существуют ровно в течение одной транзакции. Это даёт RedStone называть себя гибридной push/pull моделью: данные «толкаются» до кэширующего слоя постоянно и с высокой частотой (как push), но на сам блокчейн попадают только по требованию, в момент использования (как pull) — а не хранятся там между использованиями ни в одном из двух смыслов.

**Где обычно выбирают RedStone:** сценарии с большим количеством редко используемых котировок (длинный хвост активов, NFT, нишевые токены) — держать push-обновления для тысяч мало кому нужных прямо сейчас фидов на классической модели экономически невыгодно, а модель RedStone платит только за фактически использованные данные.

## Сводная архитектурная таблица
| | Pyth | API3 | RedStone |
|---|---|---|---|
| Источник данных | First-party (биржи, маркет-мейкеры) | First-party (сам владелец API через Airnode) | Third-party + first-party публикаторы |
| Модель доставки | Pull | Push (классический on-chain dAPI) | Гибрид: push до кэша, pull в транзакцию |
| Где физически лежат данные между обновлениями | Off-chain (Hermes), on-chain только при pull | On-chain (агрегирующий контракт) | Off-chain (DDL на Streamr/Arweave), в блокчейне — только в момент транзакции |
| Кросс-чейн доставка | Через Wormhole | Отдельные Airnode на каждой сети | Встроенный EVM-коннектор, дописывающий данные в calldata |
| Особенность | Доверительный интервал в каждом значении | OEV-доход возвращается приложению | Данные никогда не занимают постоянный storage-слот |
