# Что такое Hyperledger Fabric

## Проблема, которую решает Fabric
Публичные блокчейны вроде Ethereum — **permissionless (без разрешений)**: присоединиться к сети и увидеть все данные может кто угодно. Для многих корпоративных задач (документооборот между компаниями, отслеживание поставок, банковские расчёты) это неприемлемо — участники хотят использовать преимущества блокчейна (неизменность записей, отсутствие единой точки отказа, консенсус между несколькими сторонами), но при этом **контролировать, кто состоит в сети** и **кто что видит**.

**Hyperledger Fabric** — это **permissioned (закрытый)** блокчейн-фреймворк от Linux Foundation, специально спроектированный для использования несколькими организациями (компаниями), которые не полностью доверяют друг другу, но хотят вести общий, проверяемый реестр данных.

## Чем Fabric принципиально отличается от Ethereum-подобных сетей
| | Ethereum и подобные | Hyperledger Fabric |
|---|---|---|
| Доступ к сети | Открытый (permissionless) | Только приглашённые участники (permissioned) |
| Механизм консенсуса | Майнинг / стейкинг (PoW/PoS) | Согласование между заранее известными узлами (нет "майнинга") |
| Криптовалюта | Обязательный встроенный токен (ETH) | Нет встроенной валюты — используется только как реестр данных, если не реализован свой токен |
| Видимость данных | Все данные публичны | Можно ограничить видимость данных отдельными **каналами (channels)** между конкретными организациями |
| Смарт-контракты | Solidity, работают в EVM | JavaScript/Node.js, Java, Go — называются **chaincode** |
| Кто подтверждает транзакцию | Любой майнер/валидатор в сети | Заранее определённые узлы конкретных организаций (endorsement policy) |

## Ключевые компоненты архитектуры Fabric

| Компонент | Роль |
|---|---|
| **Peer (пир)** | Узел организации, хранящий копию реестра (ledger) и исполняющий chaincode |
| **Orderer (сортировщик)** | Узел, отвечающий за упорядочивание транзакций в блоки (аналог майнера, но без вычислительных задач) |
| **Channel (канал)** | Изолированный "подсеть"-реестр внутри общей сети — участники одного канала не видят данные другого канала |
| **Chaincode (чейнкод)** | Смарт-контракт Fabric — код, определяющий бизнес-логику работы с реестром |
| **MSP (Membership Service Provider)** | Механизм, определяющий, кто является легитимным участником организации, и связывающий сертификаты с ролями |
| **CA (Certificate Authority)** | Центр сертификации — выдаёт цифровые сертификаты участникам сети (администраторам, обычным пользователям) |
| **CouchDB / LevelDB** | База данных состояния реестра — CouchDB дополнительно поддерживает сложные запросы (rich queries) по JSON-данным |

## Как организована сеть: пример из двух организаций
```
                     ┌────────────── Канал "blockchain2024" ──────────────┐
                     │                                                     │
   ┌─────────────────┴───────┐                       ┌─────────────────┴───────┐
   │        Org1               │                       │        Org2               │
   │  ┌────────┐  ┌────────┐  │                       │  ┌────────┐  ┌────────┐  │
   │  │  Peer  │  │   CA   │  │                       │  │  Peer  │  │   CA   │  │
   │  └────────┘  └────────┘  │                       │  └────────┘  └────────┘  │
   └────────────────────────┘                        └────────────────────────┘
                     │                                                     │
                     └───────────────  Orderer  ───────────────────────────┘
```
Каждая организация имеет собственный **peer** (хранит копию реестра и исполняет chaincode) и собственный **CA** (выдаёт сертификаты своим пользователям). **Orderer** — общий для сети узел (или группа узлов), который принимает подтверждённые транзакции от всех организаций и формирует из них блоки в правильном порядке.

## Жизненный цикл транзакции в Fabric (упрощённо)
```
1. Клиент отправляет запрос на выполнение транзакции (например, "создать машину")
        ↓
2. Транзакция отправляется на peer'ы организаций, указанных в endorsement policy
        ↓
3. Каждый такой peer СИМУЛИРУЕТ выполнение chaincode и подписывает результат (endorsement)
        ↓
4. Клиент собирает подписи (endorsements) и отправляет транзакцию Orderer'у
        ↓
5. Orderer упорядочивает транзакции от разных клиентов в блок
        ↓
6. Блок рассылается всем peer'ам сети, каждый peer проверяет его и обновляет свою копию реестра
```
Важное отличие от Ethereum: сначала происходит **симуляция и одобрение (endorsement)** транзакции конкретными, заранее определёнными узлами, и только потом — **упорядочивание** в блок. В Ethereum же порядок обратный: сначала транзакция попадает в блок, и только потом она реально выполняется всеми узлами сети.

## Для каких задач подходит Fabric
- Отслеживание цепочек поставок между несколькими компаниями (кто, что и когда передал).
- Межбанковские расчёты и клиринг, где стороны заранее известны и должны быть верифицированы.
- Ведение реестров прав (собственность, лицензии) несколькими государственными или коммерческими учреждениями.
- Любые сценарии, где нужен общий, проверяемый источник истины между несколькими организациями, но публичность блокчейна вроде Ethereum избыточна или недопустима.
