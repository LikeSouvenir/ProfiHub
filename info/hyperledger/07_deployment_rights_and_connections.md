# 07. Кто может деплоить смарт-контракты и как подключаются к сети

Этот конспект отвечает на два вопроса, которые почти всегда остаются "за кадром" в типовых инструкциях: **кто именно имеет право развернуть chaincode** и **как клиентское приложение физически "находит" нужные узлы сети**.

## 7.1. Кто может развернуть chaincode — управление на уровне организаций

### Важно понять: развёртывание — это не действие одного человека
В отличие от Ethereum, где задеплоить контракт может любой владелец приватного ключа с достаточным балансом ETH, в Fabric развёртывание chaincode — это **процесс с несколькими независимыми участниками**, ни один из которых не может продавить его в одиночку.

```
Package  →  Install (на peer'ах КАЖДОЙ организации отдельно)
                    │
              Approve (КАЖДАЯ организация одобряет ОТДЕЛЬНО, своим админом)
                    │
      Проверка: достаточно ли организаций одобрило? (по политике канала)
                    │
                 Commit (фиксация в канале — выполняет любой admin,
                         но только когда кворум одобрений уже набран)
```

### Кто конкретно выполняет каждый шаг
| Шаг | Кто выполняет | Требуемые права |
|---|---|---|
| **Package** | Разработчик (может быть кто угодно) | Не требует подключения к сети — просто архивация файлов |
| **Install** | Администратор организации (admin identity) | Устанавливает пакет на peer именно **своей** организации |
| **Approve** | Администратор организации | Одобряет определение chaincode от имени **своей** организации |
| **Commit** | Любой администратор (обычно того, кто "довёл дело до конца") | Требуется, чтобы кворум организаций уже одобрил — иначе commit будет отклонён |

### Кворум одобрения — политика канала
По умолчанию используется политика **MAJORITY** (большинство) от организаций, состоящих в канале:
- Канал из 2 организаций → нужно одобрение от **обеих** (2 из 2 — это уже "большинство").
- Канал из 3 организаций → достаточно **2 из 3**.

Это можно переопределить явно при создании определения chaincode:
```bash
--signature-policy "OR('Org1MSP.member','Org2MSP.member')"    # достаточно ОДНОЙ из двух организаций
--signature-policy "AND('Org1MSP.member','Org2MSP.member','Org3MSP.member')"  # нужны ВСЕ три
```

**Вывод: развернуть работающий chaincode в одиночку, будучи администратором только одной организации из нескольких — невозможно.** Именно это и обеспечивает "доверие без доверия" между организациями: ни одна сторона не может незаметно подсунуть сети произвольный код.

## 7.2. Кто может ВЫЗЫВАТЬ уже развёрнутый chaincode
Это отдельный, более гибкий уровень прав — задаётся уже внутри самого кода chaincode (см. конспект про идентичность пользователей, `ctx.clientIdentity.getMSPID()`), а не на уровне инфраструктуры Fabric. Инфраструктура лишь гарантирует **endorsement policy** — то есть какие организации должны подтвердить транзакцию, чтобы она вообще была принята:
```bash
--signature-policy "OR('Org1MSP.member','Org2MSP.member')"
```
Эта политика означает: транзакцию должен одобрить **хотя бы один** peer одной из двух организаций (а не обе сразу) — то есть более мягкое требование, чем при *развёртывании* самого chaincode.

## 7.3. Как клиентское приложение подключается к сети — два режима

### Режим 1: Discovery Service (рекомендуемый, используется в этом курсе)
```js
await gateway.connect(ccp, {
    wallet,
    identity: 'user1',
    discovery: { enabled: true, asLocalhost: true },
});
```
При `discovery: enabled: true` приложение обращается к **одному** известному peer'у, а тот сам сообщает всей сети, какие ещё peer'ы существуют и какая между ними endorsement policy — приложению не нужно заранее знать адреса **всех** peer'ов всех организаций.
- `asLocalhost: true` — используется **только для локальной тестовой сети** (когда peer'ы доступны на `localhost` с разными портами). В реальной сети, развёрнутой на разных серверах, этот флаг должен быть `false`.

### Режим 2: явное перечисление peer'ов (без discovery)
```js
const ccp = {
    peers: {
        'peer0.org1.example.com': { url: 'grpcs://peer0.org1.example.com:7051' },
        'peer0.org2.example.com': { url: 'grpcs://peer0.org2.example.com:7051' },
    },
    // ...
};

await gateway.connect(ccp, {
    wallet,
    identity: 'user1',
    discovery: { enabled: false },
});
```
Требует, чтобы в Connection Profile были заранее прописаны все peer'ы, к которым может понадобиться обращение. Используется реже — например, при очень специфичных требованиях к маршрутизации трафика, но усложняет поддержку при масштабировании сети (добавление нового peer'а требует обновления конфигурации у всех клиентов).

## 7.4. TLS — как проверяется, что клиент общается с "настоящим" peer'ом, а не с подделкой
Все соединения между приложением и сетью идут по протоколу **gRPC поверх TLS** (`grpcs://`, а не простой `grpc://`). Каждый peer/orderer/CA имеет собственный TLS-сертификат, и Connection Profile содержит **корневые TLS-сертификаты**, которым приложение доверяет — если сертификат узла не подписан этим корнем, соединение будет отклонено на уровне TLS, ещё до какой-либо бизнес-логики.
```json
"tlsCACerts": {
    "pem": "-----BEGIN CERTIFICATE-----\nMIIC...\n-----END CERTIFICATE-----"
}
```

## 7.5. Разница между "подключением как администратор" и "подключением как клиент"
С точки зрения кода подключение выглядит одинаково (`gateway.connect(...)` с указанием `identity`) — разница только в том, **чья именно личность** передана:
```js
// Подключение от имени администратора — обычно нужно только для операций управления
await gateway.connect(ccp, { wallet, identity: 'admin', discovery: {...} });

// Подключение от имени обычного клиента — для повседневных транзакций приложения
await gateway.connect(ccp, { wallet, identity: 'user1', discovery: {...} });
```
**Хорошая практика:** обычные пользовательские операции (`AddCar`, `GetCar`) в приложении должны выполняться от имени **обычного клиента** (`user1`), а не администратора — иначе теряется весь смысл разграничения прав через `ctx.clientIdentity`, и в реестре не будет видно, кто из реальных пользователей выполнил конкретное действие (все транзакции будут "от лица admin").

## 7.6. Сводная схема всего раздела
```
                     Кто МОЖЕТ развернуть chaincode?
        Только совместное решение администраторов организаций,
        по правилу кворума канала (обычно MAJORITY)
                              │
                     Кто МОЖЕТ вызывать chaincode?
        Любой пользователь с действующим сертификатом, но КОНКРЕТНАЯ
        транзакция требует endorsement от организаций согласно
        endorsement policy И может быть дополнительно ограничена
        внутри самого кода chaincode (по MSP ID или атрибутам)
                              │
                     Как приложение находит сеть?
        Через Connection Profile (адреса + TLS-сертификаты) +
        Gateway с Discovery Service, который сам достраивает
        полную топологию сети от одной начальной точки подключения
```
