# Деплой chaincode в сеть

## Быстрый способ: скрипт deployCC
Тестовая сеть `test-network` включает готовый скрипт, автоматизирующий весь процесс развёртывания chaincode:
```bash
cd fabric-samples/test-network
./network.sh deployCC -ccn Cars -ccl javascript -ccp ../my-project/chaincode-javascript -c blockchain2024 -cci InitLedger
```

### Разбор флагов
| Флаг | Значение |
|---|---|
| `deployCC` | Команда развёртывания chaincode (Deploy ChainCode) |
| `-ccn` | Имя chaincode (chaincode name) — под этим именем к нему потом обращается клиентское приложение |
| `-ccl` | Язык реализации (chaincode language) — `javascript`, `java` или `go` |
| `-ccp` | Путь к папке с кодом chaincode (chaincode path) |
| `-c` | Имя канала, в который разворачивается chaincode |
| `-cci` | Имя функции-инициализатора (chaincode init) — вызывается автоматически один раз сразу после установки |

## Что происходит "под капотом" (жизненный цикл chaincode Fabric 2.x)
Скрипт `deployCC` объединяет несколько отдельных шагов официального жизненного цикла chaincode:
```
1. Package   — упаковка кода chaincode в архив (.tar.gz)
2. Install   — установка пакета на КАЖДЫЙ peer, который должен исполнять chaincode
3. Approve   — каждая организация ОТДЕЛЬНО одобряет определение chaincode (имя, версия, endorsement policy)
4. Commit    — после того как достаточное количество организаций одобрило — определение фиксируется в канале
5. Invoke    — вызов функции-инициализатора (например, InitLedger)
```
Такая многоступенчатая схема — намеренное архитектурное решение Fabric: ни одна отдельная организация не может в одиночку "протащить" в сеть чейнкод с произвольным поведением — требуется согласие (approve) от нужного числа участников, определяемого политикой канала.

## Обновление уже развёрнутого chaincode
При изменении кода chaincode его нельзя просто "перезаписать" — нужно развернуть новую **версию** с увеличенным номером **sequence**:
```bash
./network.sh deployCC -ccn Cars -ccl javascript -ccp ../my-project/chaincode-javascript -c blockchain2024 -ccv 2 -ccs 2
```
- `-ccv` — версия chaincode (произвольная метка, например `2`, `2.0.1`).
- `-ccs` — sequence — счётчик, который **обязательно** увеличивается на 1 при каждом новом коммите определения chaincode в канале (используется Fabric для отслеживания истории изменений определения, независимо от произвольной версии).

## Установка зависимостей перед деплоем
Так как chaincode на Node.js — это обычный npm-проект, перед разворачиванием необходимо, чтобы все зависимости (`fabric-contract-api`, `fabric-shim`) были установлены внутри папки chaincode:
```bash
cd fabric-samples/my-project/chaincode-javascript
npm install
```
Если пропустить этот шаг, `deployCC` завершится ошибкой уже на этапе упаковки/установки — peer не сможет запустить chaincode без его зависимостей.

## Проверка, что chaincode развернулся
```bash
peer lifecycle chaincode querycommitted --channelID blockchain2024 --name Cars
```
Покажет текущую закоммиченную версию и sequence chaincode `Cars` в канале `blockchain2024` — полезно для диагностики, если что-то развернулось не так, как ожидалось.

## Оптимизация процесса деплоя
1. **Не разворачивать вручную по шагам** без крайней необходимости — готовый скрипт `deployCC` покрывает подавляющее большинство учебных и небольших проектов, ручной вызов `peer lifecycle chaincode package/install/approveformyorg/commit` имеет смысл только при тонкой настройке специфичной endorsement policy.
2. **Группировать несколько контрактов в один chaincode** (через массив `contracts` в `index.js`, как в предыдущем конспекте) вместо развёртывания отдельного chaincode на каждую сущность — это уменьшает число процессов, которые peer должен поддерживать, и упрощает управление версиями.
3. **Автоматизировать пересборку и передеплой** через единый скрипт (см. следующий конспект про пользователей и финальную практику) — вручную набирать длинные команды с версией/sequence при каждом изменении кода — источник частых ошибок (забытый инкремент `-ccs`, рассинхронизация версии между организациями).
4. **Использовать одинаковую версию Node.js** внутри chaincode-контейнера и в среде разработки — расхождение версий Node может приводить к трудноуловимым различиям в поведении (например, из-за разной поддержки синтаксиса или API).
