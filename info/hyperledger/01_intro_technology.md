# 01. Ознакомление с технологией

Этот конспект — отправная точка. Если вы вообще не работали с блокчейном или работали только с публичными сетями вроде Ethereum — начните отсюда и не пропускайте разделы, дальше всё строится на этих понятиях.

## 1.1. Что такое блокчейн — предельно просто
Блокчейн — это база данных, которая:
- ведётся не одним сервером, а сразу несколькими независимыми участниками (узлами);
- каждый участник хранит полную (или частичную) копию данных;
- новую запись нельзя добавить в одиночку — нужно согласие (консенсус) нескольких участников;
- уже добавленную запись нельзя незаметно изменить или удалить.

## 1.2. Два разных мира блокчейнов
Важно сразу понять, что "блокчейн" — это не одна технология, а семейство очень разных архитектур. Курс до этого блока разбирал **Ethereum-подобные, публичные (permissionless)** сети. Hyperledger Fabric — представитель **другого мира**, и путать их подходы — главная ошибка новичков.

| | Публичные сети (Ethereum, Waves) | Hyperledger Fabric |
|---|---|---|
| Кто может подключиться к сети | Кто угодно, анонимно | Только заранее приглашённые организации |
| Нужна ли своя криптовалюта | Да, для оплаты газа | Нет, встроенной валюты нет вообще |
| Кто подтверждает транзакции | Любой майнер/валидатор в сети | Заранее определённые узлы конкретных организаций |
| Видит ли каждый участник все данные | Да, вся история публична | Нет, можно ограничить видимость через каналы |
| Язык смарт-контрактов | Solidity (компилируется в байткод EVM) | Обычный JS/Go/Java — исполняется как отдельная программа |
| Кто выдаёт "личность" (identity) | Никто — личность = пара ключей, которую можно сгенерировать самому | Центр сертификации (CA) конкретной организации |

**Вывод, который нужно запомнить на весь курс:** в Fabric нет анонимных участников и нет открытого доступа. Каждое действие в сети совершается от имени конкретного, заранее зарегистрированного участника конкретной организации.

## 1.3. Кто участвует в сети Fabric

```
┌──────────────────────────────────────────────────────────────────┐
│                         Сеть Hyperledger Fabric                    │
│                                                                    │
│   ┌──────────────── Организация 1 ────────────────┐               │
│   │                                                 │               │
│   │   CA (Certificate     Peer (узел,               │               │
│   │   Authority) —         хранящий копию            │               │
│   │   выдаёт сертификаты   реестра и исполняющий      │               │
│   │   участникам Org1      chaincode)                │               │
│   └─────────────────────────────────────────────────┘               │
│                                                                    │
│   ┌──────────────── Организация 2 ────────────────┐               │
│   │   CA                     Peer                   │               │
│   └─────────────────────────────────────────────────┘               │
│                                                                    │
│   ┌─────────────── Orderer (общий для сети) ───────┐               │
│   │   Принимает транзакции от всех организаций       │               │
│   │   и формирует из них блоки в правильном порядке   │               │
│   └─────────────────────────────────────────────────┘               │
└──────────────────────────────────────────────────────────────────┘
```

| Участник | Что делает | Аналогия |
|---|---|---|
| **Organization (организация)** | Юридическое лицо/компания — участник сети. У каждой своя инфраструктура | Банк, компания-поставщик, вуз |
| **Peer (пир)** | Узел организации. Хранит копию реестра, исполняет chaincode, подтверждает транзакции | "Бухгалтер" организации, ведущий свою копию журнала |
| **Orderer (сортировщик)** | Служебный узел сети (не принадлежит одной организации, обслуживает всех). Упорядочивает транзакции в блоки | "Секретарь", который собирает подтверждённые документы от всех и сшивает их по порядку в общий журнал |
| **CA (Certificate Authority)** | Выдаёт цифровые сертификаты участникам своей организации | "Паспортный стол" организации |
| **Channel (канал)** | Изолированное пространство внутри сети — свой отдельный реестр для конкретной группы организаций | Отдельная закрытая переписка внутри общего чата |
| **Chaincode (чейнкод)** | Смарт-контракт — программа, определяющая бизнес-логику | Регламент/бизнес-процесс, зашитый в код |
| **MSP (Membership Service Provider)** | Правила, по которым сеть понимает: "этот сертификат — от Org1, и обладает такими-то правами" | Служба безопасности, проверяющая пропуска |

## 1.4. Реестр (ledger) устроен из двух частей
Важный момент, который путает новичков: "реестр" в Fabric — это не один файл, а две связанные структуры на каждом peer'е:

| Часть | Что содержит | Аналогия |
|---|---|---|
| **Blockchain (цепочка блоков)** | Неизменяемая, последовательная история всех транзакций | Журнал всех операций по датам, ничего нельзя стереть |
| **World State (текущее состояние)** | Только **актуальные** значения — что хранится "здесь и сейчас" | Итоговая витрина остатков на складе прямо сейчас |

Когда chaincode вызывает `getState(key)` — он читает именно **World State** (актуальное значение), а не перебирает всю историю блоков. Именно World State хранится в CouchDB или LevelDB (см. следующие конспекты).

## 1.5. Как выглядит путь одной транзакции — по шагам
Это тот самый процесс, который принципиально отличает Fabric от Ethereum. Разберите его подробно — дальше он будет упоминаться при каждом объяснении API.

```
Шаг 1. Клиентское приложение формирует запрос
        "хочу вызвать функцию AddCar с такими-то аргументами"
                          │
Шаг 2. Запрос (proposal) отправляется НЕ всем, а только тем peer'ам,
        которых требует endorsement policy (политика одобрения) канала
                          │
Шаг 3. Каждый такой peer СИМУЛИРУЕТ выполнение — то есть выполняет функцию
        chaincode у себя локально, смотрит результат, но пока НИЧЕГО не
        записывает в реестр. Peer подписывает результат своей подписью
        (это называется endorsement — "одобрение")
                          │
Шаг 4. Клиент собирает достаточное количество подписей (endorsements)
        и отправляет уже подписанную транзакцию Orderer'у
                          │
Шаг 5. Orderer НЕ проверяет бизнес-логику — он просто получает транзакции
        от всех клиентов сети и укладывает их по порядку в блок
                          │
Шаг 6. Готовый блок рассылается ВСЕМ peer'ам сети (даже тем, что не
        участвовали в одобрении)
                          │
Шаг 7. Каждый peer проверяет блок (были ли собраны нужные подписи,
        не менялось ли что-то параллельно) и только теперь обновляет
        свой World State
```

**Почему это важно понимать:** ошибка в аргументах или "недостаточно средств" будет обнаружена уже на Шаге 3 (симуляция), а не после попадания в блок — клиент получит ошибку почти сразу, транзакция даже не дойдёт до Orderer'а. Это отличается от Ethereum, где неудачная транзакция всё равно попадает в блок и тратит газ.

## 1.6. Зачем вообще может понадобиться Fabric
Практические ситуации, где выбирают именно Fabric, а не публичный блокчейн:
- **Логистика/цепочки поставок** между несколькими компаниями, которые не готовы публиковать свои данные всему миру, но хотят проверяемый общий журнал.
- **Межбанковские расчёты**, где участники заранее известны и юридически ответственны за свои действия.
- **Ведение реестров** (собственность, дипломы, сертификаты качества) несколькими доверенными организациями совместно.
- Любая ситуация вида: "нам нужен общий, неизменяемый источник истины между 2-10 конкретными организациями, но без полной публичности".

## 1.7. Мини-словарь терминов (держите под рукой весь курс)
| Термин | Значение одной фразой |
|---|---|
| Peer | Узел организации, хранящий реестр |
| Orderer | Узел, упорядочивающий транзакции в блоки |
| Channel | Изолированный реестр внутри сети |
| Chaincode | Смарт-контракт Fabric |
| MSP | Правила определения "кто есть кто" в сети |
| CA | Служба, выдающая сертификаты |
| Identity | Сертификат X.509 конкретного участника |
| Wallet | Локальное хранилище личностей на стороне приложения |
| Endorsement | Одобрение (подпись) транзакции конкретным peer'ом |
| World State | Текущие, актуальные значения реестра |
| Ledger | И блокчейн, и world state вместе |

Дальше в курсе каждый из этих терминов будет разобран отдельно и подробно, с реальными командами и кодом.
