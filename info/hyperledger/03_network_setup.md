# Установка Fabric и запуск тестовой сети

## Установка бинарников и образов Fabric
В корневой папке будущего проекта (внутри WSL или через `wsl <команда>` из Windows):
```bash
curl -sSLO https://raw.githubusercontent.com/hyperledger/fabric/main/scripts/install-fabric.sh
chmod +x install-fabric.sh
./install-fabric.sh
```
Этот скрипт:
1. Клонирует репозиторий **fabric-samples** — набор готовых примеров, скриптов и тестовой сети.
2. Скачивает необходимые **Docker-образы** (peer, orderer, CA, CouchDB и другие служебные образы).
3. Скачивает **бинарные файлы** самого Fabric (`peer`, `orderer`, `cryptogen`, `configtxgen` и т.д.) и добавляет их в `fabric-samples/bin`.

*Из всего репозитория `fabric-samples` для базовой разработки реально нужны лишь несколько папок: `test-network` (тестовая сеть), `bin` (бинарники), `builders` и `config` (служебные файлы для запуска chaincode) — остальные примеры можно не трогать.*

## Структура важных папок fabric-samples
```
fabric-samples/
├── bin/                    # Бинарники: peer, orderer, cryptogen, configtxgen...
├── builders/               # Скрипты сборки chaincode
├── config/                 # Базовые конфигурационные файлы
├── test-network/           # Готовая тестовая сеть из 2 организаций — основная рабочая папка
│   ├── organizations/      # Сертификаты и MSP-данные организаций
│   ├── addOrg3/            # Готовый скрипт добавления третьей организации
│   └── network.sh          # Главный скрипт управления сетью
└── token-erc-20/           # Пример реализации токена (см. отдельный конспект)
```

## Поднятие тестовой сети и создание канала
```bash
cd fabric-samples/test-network
./network.sh up createChannel -c blockchain2024 -ca -s couchdb
```

### Разбор флагов
| Флаг/аргумент | Значение |
|---|---|
| `up` | Поднять сеть: запустить контейнеры peer'ов и orderer'а обеих организаций |
| `createChannel` | Сразу же создать канал и подключить к нему peer'ы обеих организаций |
| `-c blockchain2024` | Имя создаваемого канала |
| `-ca` | Использовать собственные Certificate Authority для каждой организации (а не заранее сгенерированные статические сертификаты через `cryptogen`) — необходимо, если дальше планируется регистрировать реальных пользователей через CA |
| `-s couchdb` | Использовать **CouchDB** в качестве базы состояния (вместо LevelDB по умолчанию) — нужен, если chaincode должен уметь выполнять сложные запросы по полям JSON-документов |

*Важно: сеть обязательно нужно поднять этой командой **хотя бы один раз** до первого вызова `./network.sh down`. Если выключить сеть до первого успешного запуска, служебные файлы окружения могут остаться в неконсистентном состоянии, и повторный запуск в той же папке будет завершаться ошибками.*

## Остановка и полная очистка сети
```bash
./network.sh down
```
Останавливает и удаляет все связанные контейнеры, сети Docker и сгенерированные крипто-материалы — фактически "сбрасывает" тестовую сеть в исходное состояние.

## Добавление третьей организации
Для сценариев, где нужно больше двух участников (например, чтобы отдельно ограничивать права какой-то функции чейнкода для конкретной организации):
```bash
cd test-network/addOrg3
./addOrg3.sh up -c blockchain2024 -ca -s couchdb
```
Скрипт генерирует материалы для новой организации (Org3), подключает её peer к уже существующему каналу `blockchain2024` — сеть при этом не нужно останавливать и поднимать заново.

## Переименование организаций: как это делают "по инструкции" и как оптимальнее

### Способ "в лоб" (не рекомендуется)
Часто предлагаемый способ — открыть весь `fabric-samples` в редакторе, найти все вхождения `Org1`, `Org2`, `OrgXMSP` и заменить их на нужные названия через глобальный поиск-замену по сотням файлов. У этого подхода есть серьёзные недостатки:
- Крипто-материалы (`cryptogen`) генерируются заново при каждом запуске сети — переименование "руками" в уже сгенерированных файлах бессмысленно после `./network.sh down` и повторного `up`.
- Легко случайно заменить лишнее вхождение подстроки в неподходящем месте (например, в бинарных или сгенерированных файлах), что ломает сеть.
- При добавлении организации (`addOrg3`) или пересборке сети всю замену придётся повторять заново.

### Более оптимальный способ
Если реально нужны "говорящие" названия организаций (а не `Org1`/`Org2`), правильное место для этого — файлы конфигурации **генерации** крипто-материалов и конфигурации сети, которые читаются при **каждом** поднятии сети, а не после:
```
test-network/organizations/cryptogen/crypto-config-org1.yaml
test-network/organizations/cryptogen/crypto-config-org2.yaml
```
Именно в этих файлах меняется поле `Name` — при следующем `./network.sh up` `cryptogen` сгенерирует материалы уже с новыми именами автоматически, без ручной правки десятков производных файлов.

**Ещё более практичный подход для учебных и большинства реальных задач:** оставить организации с именами по умолчанию (`Org1`, `Org2`) на уровне инфраструктуры Fabric, а "человекочитаемые" названия (например, "ProfiShop", "SupplierCo") использовать только на уровне **вашего собственного приложения** — как значение поля в объекте, а не как переопределение системных MSP ID. Так сеть остаётся полностью совместимой со стандартными скриптами `test-network` и `addOrg3`, а бизнес-смысл организации остаётся в коде приложения, где его проще поддерживать и не нужно бояться сломать инфраструктуру Fabric при каждом пересоздании сети.
