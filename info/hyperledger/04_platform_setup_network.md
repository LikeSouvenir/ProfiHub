# 04. Настройка платформы: поднятие сети и каналов

## 4.1. Главный инструмент: network.sh
Вся тестовая сеть управляется одним скриптом — `fabric-samples/test-network/network.sh`. Он "прячет" за собой десятки низкоуровневых команд (`cryptogen`, `configtxgen`, `docker compose`, `peer channel`) — понимание этого важно: когда что-то не работает, полезно знать, что можно "провалиться" на уровень ниже и вызвать нужную команду вручную.

```bash
cd ~/projects/hl-project/fabric-samples/test-network
```
Все команды этого конспекта выполняются именно из этой папки.

## 4.2. Полная таблица команд network.sh
| Команда | Что делает |
|---|---|
| `./network.sh up` | Поднять сеть (только Org1, Org2, Orderer) — БЕЗ создания канала |
| `./network.sh up createChannel` | Поднять сеть И сразу создать канал | 
| `./network.sh createChannel` | Создать канал на уже поднятой сети |
| `./network.sh deployCC` | Развернуть chaincode (см. отдельный конспект про деплой) |
| `./network.sh down` | Остановить сеть, удалить все контейнеры и сгенерированные крипто-материалы |
| `./network.sh restart` | То же самое, что `down` + `up` |

## 4.3. Полная таблица флагов
| Флаг | Применяется к | Значение | Пример |
|---|---|---|---|
| `-c` | `createChannel`, `deployCC` | Имя канала | `-c blockchain2024` |
| `-ca` | `up` | Использовать полноценные Certificate Authority вместо статичных сертификатов `cryptogen` | `-ca` |
| `-s` | `up` | Тип базы состояния: `leveldb` (по умолчанию) или `couchdb` | `-s couchdb` |
| `-ccn` | `deployCC` | Имя chaincode | `-ccn Cars` |
| `-ccl` | `deployCC` | Язык chaincode: `javascript`, `typescript`, `go`, `java` | `-ccl javascript` |
| `-ccp` | `deployCC` | Путь к папке с кодом chaincode | `-ccp ../my-project/chaincode-javascript` |
| `-cci` | `deployCC` | Имя функции-инициализатора | `-cci InitLedger` |
| `-ccv` | `deployCC` | Версия chaincode (для обновлений) | `-ccv 2` |
| `-ccs` | `deployCC` | Sequence — счётчик коммитов определения chaincode | `-ccs 2` |
| `-verbose` | любая | Подробный вывод логов выполнения | `-verbose` |

## 4.4. cryptogen vs Certificate Authority (-ca) — в чём разница и что выбрать

| | Без `-ca` (по умолчанию, `cryptogen`) | С флагом `-ca` |
|---|---|---|
| Как выдаются сертификаты | Заранее, статично сгенерированы утилитой `cryptogen` при поднятии сети | Полноценный сервис CA работает как контейнер, выдаёт сертификаты "по запросу" |
| Можно ли регистрировать новых пользователей после старта сети | ❌ Нет — набор личностей фиксирован при генерации | ✅ Да — через `register`/`enroll`, сколько угодно новых пользователей |
| Когда уместно | Быстрый тест самого chaincode, без реальных пользователей приложения | Всегда, если приложение должно регистрировать реальных пользователей (админов, клиентов) через API |

**Вывод: для этого курса `-ca` обязателен всегда** — без него не будет работать вся тема про создание пользователей (см. конспект 06).

## 4.5. LevelDB vs CouchDB — в чём разница и что выбрать
| | LevelDB (по умолчанию) | CouchDB (`-s couchdb`) |
|---|---|---|
| Формат хранения | Пары ключ-значение, без понимания структуры значения | Понимает, что значение — это JSON, может искать по его полям |
| Поддержка сложных запросов (`rich queries`) | ❌ Нет | ✅ Да — `getQueryResult` с CouchDB-запросом внутри chaincode |
| Скорость простых операций (`getState`/`putState` по ключу) | Немного быстрее | Немного медленнее (сопоставимо для учебных задач) |
| Когда выбирать | Простой chaincode без поиска по полям | Chaincode, где нужно искать "все машины красного цвета" и подобное — то есть почти всегда в реальных проектах |

**Вывод: для этого курса `-s couchdb` обязателен** — иначе `GetAllCars`-подобные запросы с фильтрацией по полю пришлось бы делать вручную, перебирая весь диапазон ключей (как в самом первом, неоптимальном примере chaincode).

## 4.6. Пошагово: поднятие сети и создание канала
```bash
./network.sh up createChannel -c blockchain2024 -ca -s couchdb
```
Дождитесь строки `Channel 'blockchain2024' joined` в конце вывода — это подтверждение успеха.

### ✅ Проверка
```bash
docker ps
```
Ожидаемый список контейнеров:
```
peer0.org1.example.com
peer0.org2.example.com
orderer.example.com
ca_org1
ca_org2
ca_orderer
couchdb0
couchdb1
```

Проверка канала:
```bash
peer channel list
```

```
    │   ├── peers/peer0.org1.example.com/       # MSP и TLS-сертификаты конкретного peer'а
    │   └── connection-org1.json                # ← Connection Profile — см. ниже
    └── org2.example.com/
        └── ... (аналогично)
```

## 4.8. Connection Profile — как приложение "узнаёт" адрес сети
Файл `connection-org1.json` — это JSON-описание того, как клиентскому приложению подключиться к сети от имени Org1: адреса peer'ов, адрес CA, TLS-сертификаты для проверки подлинности узлов.
```json
{
  "peers": {
    "peer0.org1.example.com": {
      "url": "grpcs://localhost:7051",
      "tlsCACerts": { "pem": "-----BEGIN CERTIFICATE-----..." }
    }
  },
  "certificateAuthorities": {
    "ca.org1.example.com": {
      "url": "https://localhost:7054",
      "caName": "ca-org1"
    }
  }
}
```
Именно этот файл читает клиентское приложение (см. конспект про API) функцией `buildCCPOrg(...)` — он и есть "инструкция", куда подключаться. Менять его руками не нужно — он полностью автогенерируется скриптом `network.sh` при каждом поднятии сети.

## 4.9. Добавление третьей организации
```bash
cd addOrg3
./addOrg3.sh up -c blockchain2024 -ca -s couchdb
cd ..
```
Скрипт генерирует материалы для Org3 (свой CA, свой peer) и подключает её к уже существующему каналу `blockchain2024`, не останавливая сеть.

### ✅ Проверка
```bash
docker ps | grep org3
```
Должны появиться `peer0.org3.example.com`, `ca_org3`, `couchdb2`.

## 4.10. Остановка сети
```bash
./network.sh down
```
Удаляет **все** контейнеры и **все** сгенерированные крипто-материалы. После этой команды все прежние "личности" (wallet) на стороне приложения становятся недействительными — подробно об этом в конспекте про пользователей.

## 4.11. Частые ошибки этого этапа
| Ошибка | Причина | Решение |
|---|---|---|
| `Error: failed to create deliver client for orderer` | Сеть ещё не успела полностью подняться | Подождать 10-15 секунд и повторить команду |
| `Channel already exists` | Канал с таким именем уже создан ранее | Использовать `./network.sh down`, затем поднять заново |
| После `down` до первого успешного `up` сеть не запускается | Частичное состояние осталось от прерванного первого запуска | Вручную удалить `docker network prune`, `docker volume prune`, и попробовать снова |
| `port is already allocated` | Порт 7051/7054/5984 уже занят другим процессом/контейнером | `docker ps -a`, остановить конфликтующий контейнер, либо `./network.sh down` для полной очистки |
