# 06. Способы создания пользователей — все варианты

## 6.1. Важный принцип: нет "единого админа сети"
В Fabric **нет** одного суперпользователя, управляющего всей сетью. У **каждой организации свой собственный CA**, и администратор Org1 не может ничего создавать в Org2 — организации полностью независимы друг от друга в вопросах управления своими пользователями. Это прямое следствие децентрализованной природы Fabric.

```
CA организации Org1                    CA организации Org2
      │                                        │
   admin (org1)                            admin (org2)
      │                                        │
   регистрирует                            регистрирует
      │                                        │
 user1, user2...(org1)                   user1, user2...(org2)
```
`user1` организации Org1 и `user1` организации Org2 — это **два совершенно разных** участника сети, несмотря на одинаковый `enrollmentID` — их различает `mspId` (`Org1MSP` vs `Org2MSP`), это будет видно и в структуре Wallet, и внутри chaincode.

## 6.2. Способ 1 — через Node.js SDK (основной способ для приложений)
Именно этот способ используется в API, который приложение показывает пользователям (см. конспект про написание API). Уже разбирался в конспекте 05, повторим кратко порядок:
```js
// 1. Администратор организации enroll'ится один раз, по заранее известным данным CA
await caClient.enroll({ enrollmentID: 'admin', enrollmentSecret: 'adminpw' });

// 2. От имени администратора регистрируется новый пользователь
const secret = await caClient.register({ enrollmentID: 'user1', role: 'client', affiliation: 'org1.department1' }, adminUser);

// 3. Пользователь enroll'ится по выданному секрету — получает сертификат
await caClient.enroll({ enrollmentID: 'user1', enrollmentSecret: secret });
```
Это способ, который стоит использовать в реальном приложении — именно он лежит в основе эндпоинтов `/enrollAdmin` и `/enrollUser` в конспекте про API.

## 6.3. Способ 2 — через консольную утилиту fabric-ca-client (без единой строчки кода)
Fabric поставляет готовую CLI-утилиту — удобно для ручного создания пользователей при отладке, без написания скрипта:
```bash
export FABRIC_CA_CLIENT_HOME=~/projects/hl-project/fabric-ca-client-org1

# Enroll администратора
fabric-ca-client enroll -u https://admin:adminpw@localhost:7054 --caname ca-org1 --tls.certfiles "$TLS_CERT_PATH"

# Регистрация нового пользователя (от имени уже enroll'нутого администратора)
fabric-ca-client register --caname ca-org1 --id.name user1 --id.secret user1pw --id.type client --tls.certfiles "$TLS_CERT_PATH"

# Enroll этого пользователя
fabric-ca-client enroll -u https://user1:user1pw@localhost:7054 --caname ca-org1 --tls.certfiles "$TLS_CERT_PATH"
```
Разница с SDK-способом только в интерфейсе (консоль вместо кода) — внутренние шаги (`register` → `enroll`) абсолютно те же самые.

## 6.4. Способ 3 — напрямую через REST API самого CA-сервера
Fabric CA — это, по сути, обычный HTTPS-сервер со своим REST API, поэтому пользователя можно создать даже без клиентских библиотек, через обычный `curl`:
```bash
# Enroll администратора (Basic Auth: admin:adminpw)
curl -X POST https://localhost:7054/api/v1/enroll \
  -u admin:adminpw \
  --cacert "$TLS_CERT_PATH"

# Регистрация нового пользователя (нужен Bearer-токен администратора — получается на предыдущем шаге)
curl -X POST https://localhost:7054/api/v1/register \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"id": "user1", "type": "client", "affiliation": "org1.department1"}' \
  --cacert "$TLS_CERT_PATH"
```
На практике этот способ используют редко (SDK удобнее), но важно понимать: `fabric-ca-client` (и SDK, и CLI) — это просто удобная обёртка над обычным HTTP REST API, а не "магия" — при желании интеграцию с CA можно написать на любом языке, который умеет делать HTTPS-запросы.

## 6.5. Роли пользователя (role) — что означают
| Роль | Значение |
|---|---|
| `client` | Обычный пользователь приложения — отправляет транзакции, ничем не управляет |
| `admin` | Администратор организации — может регистрировать других пользователей, устанавливать/одобрять chaincode |
| `peer` | Специальная роль для идентичности самого peer-узла (не для людей) |
| `orderer` | Специальная роль для идентичности orderer-узла |

## 6.6. Affiliation — подразделения внутри организации
`affiliation` — способ группировать пользователей внутри одной организации (например, `org1.department1`, `org1.department2`) — используется в первую очередь для более гибкого разграничения того, кто кого может регистрировать (администратор одного отдела не обязан иметь право регистрировать пользователей другого).
```bash
fabric-ca-client affiliation list                          # посмотреть все существующие affiliation
fabric-ca-client affiliation add org1.department2           # добавить новое подразделение
```

## 6.7. Проверка существующих пользователей CA
```bash
fabric-ca-client identity list --caname ca-org1
```
Выведет список всех зарегистрированных (через `register`) личностей этого CA с их ролями и affiliation.

## 6.8. Отзыв пользователя (revoke)
Если сотрудник уволился или сертификат скомпрометирован:
```js
await caClient.revoke({
    enrollmentID: 'user1',
    reason: 'cessationofoperation',
}, adminUser);
```
После `revoke` сертификат помечается недействительным — но чтобы сеть **реально** начала отклонять транзакции с этим сертификатом, отозванный сертификат должен попасть в **CRL (Certificate Revocation List)**, которую периодически подтягивают peer'ы. Это важный практический нюанс: `revoke` — не мгновенная блокировка "здесь и сейчас" на все узлы сети, а начало процесса распространения информации об отзыве.

## 6.9. Сводная таблица: какой способ когда использовать
| Способ | Когда использовать |
|---|---|
| Node.js SDK (`fabric-ca-client` как библиотека) | В реальном приложении — именно так регистрация встраивается в API/фронтенд |
| CLI-утилита `fabric-ca-client` | Ручная отладка, разовая настройка сети без написания кода |
| Прямой REST API | Интеграция с языком, для которого нет готового Fabric SDK, либо для полного понимания "что происходит под капотом" |

## 6.10. Практический пример: полная иерархия для двух организаций
```bash
# Организация 1
enrollAdmin('org1')                                    # admin org1
enrollUser('org1', 'director1')                         # обычный сотрудник org1
enrollUser('org1', 'manager1')                          # ещё один сотрудник org1

# Организация 2
enrollAdmin('org2')                                    # admin org2 — СОВЕРШЕННО другой CA
enrollUser('org2', 'supplier1')                          # сотрудник org2
```
После этого в системе одновременно существуют 5 независимых личностей, каждая со своим MSP ID, каждая может подписывать транзакции только от своего имени, но видеть данные общего канала `blockchain2024`, к которому подключены обе организации.
